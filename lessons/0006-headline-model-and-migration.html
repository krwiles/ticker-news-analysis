The Headline model and migration

The first real table in this project — and the first time two different tools need two different connection strings to the same database.

Why dbmate, not Alembic

SQLAlchemy is an ORM — it maps Python classes onto tables, it doesn't create or alter those tables itself. Most FastAPI+SQLAlchemy projects reach for Alembic, which generates migrations from your models by diffing them against the database. This project's stack was chosen to learn a specific insider list instead, which named dbmate explicitly: a framework-independent tool that migrates via plain .sql files you write by hand, with a -- migrate:up / -- migrate:down pair per file.

db/migrations/20260909125433_create_headlines.sql

-- migrate:up
CREATE TABLE headlines (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ticker TEXT NOT NULL,
    title TEXT NOT NULL,
    url TEXT NOT NULL,
    category TEXT NOT NULL CHECK (category IN ('news', 'filing')),
    provider TEXT NOT NULL,
    raw_content TEXT,
    published_at TIMESTAMPTZ NOT NULL,
    fetched_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX headlines_url_idx ON headlines (url);
CREATE INDEX headlines_ticker_published_at_idx ON headlines (ticker, published_at DESC);

-- migrate:down
DROP TABLE headlines;

The trade-off, honestly: Alembic keeps migrations and models from drifting apart automatically. With dbmate, the SQL above and the Python model below have to be kept in sync by hand — real cost, accepted for matching the actual insider stack list rather than substituting a more common tool.

Two different DATABASE_URLs, on purpose

dbmate runs on your host machine, not inside a container — so it needs postgres://ticker:ticker@localhost:5432/ticker?sslmode=disable, reaching Postgres through the port docker-compose maps to your Mac. The app itself needs postgresql+asyncpg://ticker:ticker@db:5432/ticker — a different URL scheme (+asyncpg tells SQLAlchemy which driver to use) and a different host (db, the compose network name from lesson 5, not localhost).

Both are named DATABASE_URL, and that's not a collision: docker-compose.yml sets the app's version directly in each service's environment: block, which always wins over whatever's in .env for a container. dbmate, running on the host, reads .env's copy directly. Two tools, two audiences, one file, no actual conflict — but worth knowing explicitly, because the symptom of missing this is a confusing "connection refused" that has nothing to do with Postgres actually being down.

SQLAlchemy 2.0's Mapped / mapped_column style

backend/src/ticker_backend/models.py

class Headline(Base):
    __tablename__ = "headlines"

    id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), primary_key=True, server_default=text("gen_random_uuid()")
    )
    ticker: Mapped[str] = mapped_column(Text)
    category: Mapped[Literal["news", "filing"]] = mapped_column(Text)
    published_at: Mapped[datetime] = mapped_column(DateTime(timezone=True))
    fetched_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )

Mapped[X] is the Python-side type; mapped_column(...) is the actual column definition. Using Literal["news", "filing"] for category — rather than plain str — gets a type checker to flag a typo'd category at write time, even though the column itself is just TEXT underneath.

Why a server-generated UUID

server_default=text("gen_random_uuid()") means Postgres generates the id, not Python — gen_random_uuid() has been built into Postgres since version 13, no extension required. The database becomes the single source of truth for identity, and SQLAlchemy fetches the generated value back via RETURNING after insert, so headline.id is populated immediately without a second round trip.

category: a CHECK constraint, not a native enum

Postgres has real enum types, but they're awkward to evolve — adding a new value means an ALTER TYPE, and older Postgres versions couldn't even do that inside a transaction. A CHECK constraint on a plain TEXT column is one line to change later (ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT ...), at the cost of the allowed values living outside Python's type system — which the Literal hint above claws part of that back.

Check your understanding

Q1. category is a plain TEXT column. Why does inserting category='rumor' fail at the database level rather than just at the Python/Pydantic level?

Reveal answer

The migration adds CHECK (category IN ('news', 'filing')) directly on the column. Even a raw INSERT from psql, bypassing Python entirely, would be rejected — the constraint lives in Postgres, not in the ORM.

Q2. You run dbmate up from your Mac's terminal. Which DATABASE_URL does it use — the one in docker-compose.yml, or the one in .env?

Reveal answer

.env's. dbmate runs on the host, outside docker-compose entirely — it never sees docker-compose.yml's environment: block, which only applies to containers.
