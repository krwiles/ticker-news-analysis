FastAPI: serving both the API and the UI

What's actually inside create_app() — path operations, routers, and the SPA fallback.

Path operations: the actual unit of FastAPI

Lesson 1 showed api mode as "the branch that doesn't call app.frontend()." What it does instead is serve whatever path operations got registered — FastAPI's term for "a function tied to a URL and an HTTP method." Every one of these starts as a plain decorated function:

backend/src/ticker_backend/health.py

router = APIRouter()

@router.get("/health")
async def health() -> dict:
    db_status = await check_db()
    redis_status, redis_client = await check_redis()
    worker_status = await check_worker(redis_client)
    ...
    return {"api": {...}, "db": db_status, "redis": redis_status, "worker": worker_status}

@router.get("/health") is the whole registration: HTTP method (GET), path (/health), and the function to call. Return a Python dict and FastAPI serializes it to JSON automatically — no separate serializer to write or configure.

An APIRouter is a bucket of path operations that can be built in one file and wired into the app elsewhere. Right now there's exactly one router (health_router), but the pattern is what lets a real app split by feature — a tickers router, an articles router — without one giant main.py.

This is the seam lesson 5 will use: a new tickers.py module with its own APIRouter, included the same way.

backend/src/ticker_backend/main.py

def create_app() -> FastAPI:
    app = FastAPI(title="ticker-news-analysis", version="0.1.0")

    if settings.app_mode == "api":
        app.add_middleware(CORSMiddleware, allow_origins=[settings.ui_origin], ...)
        app.include_router(health_router)       # the full aggregate
    else:
        app.include_router(ui_health_router)    # a trivial self-check only
        app.frontend("/", directory=STATIC_DIR)

    return app

include_router copies every path operation the router defined onto the app — a different router per mode, not the same one twice. That "different router" part wasn't the original design; it's a fix, and the story of why is worth knowing.

Earlier, include_router(health_router) ran unconditionally — both modes got the exact same full aggregate. Because the frontend's fetch was a relative URL (fetch("/health")), the browser was actually calling whichever container served the page — ui — not api at all, and it only ever looked like it worked because ui happened to expose an identical copy of the aggregate by accident. See docs/adr/0002-cors-over-shared-health-router.md for the full reasoning; the short version: each container should only report on what it actually is, so ui now gets a trivial {"status": "ok"}, api keeps the one real aggregate, and the frontend calls api's origin explicitly — which makes it a genuine cross-origin request, which is what the CORSMiddleware line is for.

Low-priority routes: how app.frontend() avoids a fight over its own container's routes

In ui mode, the same app also calls app.frontend("/", directory=STATIC_DIR), which hands out the built React files. Naively, mounting something at "/" sounds like it should swallow every path — including the trivial /health route just above it. It doesn't, and the reason is worth being precise about, because it's a real design choice FastAPI made, not an accident of file order:

app.frontend() routes are explicitly low-priority. FastAPI always checks normal path operations first, regardless of where app.frontend() was called relative to them. Move the call to the top of create_app() and /health would still win.

That's a deliberate improvement over the older pattern (mounting StaticFiles(html=True) directly), which did depend on registration order — mount it before your routes and it would have swallowed them. The comment in main.py calls this out directly: that's the bug class this API was built to make impossible.

The SPA fallback, and how it actually decides

When a request doesn't match a real file in the build or a path operation, app.frontend() has to decide: 404, or serve index.html so React Router can take over client-side? It looks at the request's Accept header — not the URL shape — to tell a browser navigating to a page apart from, say, a fetch for a missing asset:

Verified directly against the running container, not just read from source:

Empirical check beats a docs skim — this is what actually happened when it ran. 
$ curl -o /dev/null -w "%{http_code}\n" http://localhost:3000/some/client/route
404

$ curl -o /dev/null -w "%{http_code}\n" -H "Accept: text/html" http://localhost:3000/some/client/route
200

A real browser always sends Accept: text/html (or similar) when navigating, so this is invisible in practice — but it's why a bare curl with no headers looked "broken" during testing when it wasn't. The rule: no matching file or route, and the request looks like a page navigation → serve index.html, status 200. Otherwise → 404.

Check your understanding

Q1. In the ui branch, you move app.frontend("/", directory=STATIC_DIR) above include_router(ui_health_router). Does ui's /health still work?

Reveal answer

Yes. app.frontend() routes are always low-priority regardless of registration order, so normal path operations are checked first either way.

Q2. A request comes in for /nonexistent-file.png with no special Accept header (like a plain curl). What status code, and why?

Reveal answer

404. It doesn't match a real file or a path operation, and without Accept: text/html it isn't recognized as a page-navigation request, so it doesn't qualify for the index.html fallback either.

Q3. A request for /health arrives at the api container with header Origin: http://evil.example.com. Does the server refuse the request?

Reveal answer

No — the server still responds 200. CORS isn't enforced by the server rejecting the request; it's enforced by the browser, which withholds the response body from JavaScript on that origin because the response's Access-Control-Allow-Origin header doesn't match. A non-browser client (like curl) never enforces this at all.
