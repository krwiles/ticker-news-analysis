Migration: sentiment columns

Schema before logic, same shape as lessons 6 and 17 — and the same "derive, don't store" principle from lesson 17, reapplied to a brand new feature before any code needed correcting it this time.

No sentiment-computing logic yet — that's lesson 26. This lesson is purely six new nullable columns: four on headlines, two on stories. Everything here comes from a real grilling round on spec 0005 (docs/specs/0005-headline-sentiment-analysis.md) and its technical approach (docs/adr/0014-sentiment-analysis-technical-approach.md) — this lesson is where those decisions actually became a schema.

The question lesson 17 already answered, asked again on purpose

Spec 0005 fixes three sentiment values — positive, neutral, negative — plus a 0-100 numeric score the model actually produces. The enum is derived from the score by a fixed rule, never asked of the model independently. So: does the enum get its own column too?

This is the exact same question lesson 17 already worked through for stories.primary_headline_id — is this fact actually new information, or is it fully determined by data already stored elsewhere? The enum is a pure function of sentiment_score. Storing it as a second column recreates precisely the "two facts that must stay in sync" problem lesson 17 removed on purpose (see ADR 0009).

Decision: no stored enum, on either table. Only sentiment_score (an integer, 0-100) gets a column. Whatever later code turns a score into "positive"/"neutral"/ "negative" for display does it by reading the number, every time — never by reading a second, separately-written column that could quietly drift out of sync with the first.

Why a bare NULL isn't enough: the case for sentiment_status

Every new headlines column is nullable, same staged-rollout pattern outlet/ summary/story_id already used. But sentiment runs as its own background job, decoupled from the search that persisted the headline in the first place — and that raises a real question a synchronous feature never had to answer: once a poll finds sentiment_score IS NULL, what does that actually mean?

It's ambiguous three different ways: still being computed (keep polling, it's coming); skipped, because the OpenAI dependency wasn't configured when this run happened (won't come this run, but isn't permanently dead either); or errored, a real attempt that failed (same deal). A frontend that can't tell these apart either polls forever for something that will never resolve this run, or gives up on an arbitrary timeout instead of actually knowing what happened. sentiment_status — ok/ skipped/error, itself nullable — is what makes that distinction real.

Why stories doesn't get an equivalent status column

A natural instinct, once headlines has one: shouldn't the Story-level aggregate need the same thing? It doesn't, and the reason is worth sitting with rather than just copying the pattern reflexively. sentiment_score_count already answers the only question the aggregate actually needs answered:

  • count > 0 — there's a real average, show it.
  • count == 0 — there isn't one yet.

The aggregate never needs to know why the count is still zero — that reason lives on each individual member's own sentiment_status, visible on that member's own pill if you actually look at it. And a page-level "is sentiment configured and working" signal (its own component, mirroring GroupingStatus) already answers the dependency-health question once, for the whole page. A Story-level copy of that same signal would just be redundant — the same "does this column encode anything new?" test lesson 17 already applied, this time answered before any code shipped, not after.

The other real decision hiding in sentiment_score_count: what actually gets counted

stories.sentiment_average is an incrementally-updated running average, not a live AVG(...) query recomputed on every read — a deliberate exception to lesson 17's own derive-don't-store precedent, chosen because it needs the least new code (the standard cumulative-moving- average update, new_average = old_average + (new_score - old_average) / new_count, is O(1) per new member instead of re-scanning every member on every read). That's lesson 26's problem to build, not this one's — but this lesson still has to get the count right, because it decides what the eventual average will and won't include.

Only a member that actually reaches sentiment_status = 'ok' ever increments it. A skipped or errored member is excluded entirely — never treated as a zero. Why this matters: sentiment isn't fully permanent the way it first looked. Only a real score is permanent; skipped/error stay eligible for a later retry, if some future request happens to touch that same headline again. If a skipped member had been counted as a zero contribution now, a later successful retry would need to "un-count" a phantom value that was never real — exactly the kind of redundant, drift-prone state this project keeps choosing not to build.

Verified live before writing a single line of the migration

ALTER TABLE ... ADD COLUMN on a table with real, existing rows has a reputation for being slow or lock-heavy on some databases — worth actually checking against the real dev database (headlines: 2000+ rows, stories: 800+ rows) rather than assuming Postgres 17 handles it the same way: 

BEGIN;
ALTER TABLE headlines ADD COLUMN sentiment_score_test INTEGER;      -- 1.397 ms
ALTER TABLE headlines ADD COLUMN sentiment_status_test TEXT;        -- 0.249 ms
ALTER TABLE stories ADD COLUMN sentiment_score_count_test
  INTEGER NOT NULL DEFAULT 0;                                       -- 1.649 ms
ROLLBACK;

All three, including the NOT NULL DEFAULT 0 one, completed in under 2ms. Postgres 11+ optimizes a constant default to a metadata-only change — no full table rewrite, no real lock concern at this project's scale. Run inside a transaction and rolled back, so nothing was actually persisted by the check itself; the real migration ran separately, for real, afterward.

Check your understanding

Q1. Why doesn't sentiment (the positive/neutral/negative enum) get its own column?

Reveal answer

It's fully determined by sentiment_score via a fixed threshold rule -- storing it separately would create two facts that have to agree with each other, with nothing enforcing that they do. Same principle as lesson 17's stories.primary_headline_id: if a fact is fully derivable from data already stored, storing it again is redundant state, not a safety net.

Q2. A Headline's sentiment_status is 'error'. Is that permanent?

Reveal answer

No -- only a real score (sentiment_status eventually becoming 'ok') is permanent. 'error' and 'skipped' both stay eligible for a later retry, if some future request happens to include that same headline again. That's exactly why a Story's sentiment_score_count only increments on 'ok' -- an 'error'ed member might still succeed later, and shouldn't have been counted as a zero in the meantime.
