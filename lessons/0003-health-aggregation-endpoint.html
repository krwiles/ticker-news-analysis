The /health aggregation endpoint

One path operation, three real checks, and why it doesn't just return {"ok": true}.

Why a real check instead of a stub

The easy version of this endpoint is one line: return {"status": "ok"}. It would satisfy "the API responded," but it would tell you nothing true about the database, Redis, or the worker — a status page built on that is decoration, not a status page. health.py does the more honest thing: it actually talks to each dependency and reports what happened.

backend/src/ticker_backend/health.py

async def check_db() -> dict:
    try:
        async with _engine.connect() as conn:
            await conn.execute(text("SELECT 1"))
        return {"status": "ok"}
    except Exception as exc:
        return {"status": "error", "detail": str(exc)}

_engine is a SQLAlchemy async engine — the connection-managing object the rest of the app (starting lesson 6) will use for every database interaction. SELECT 1 is the smallest possible real query: not asking about any table, just "can I round-trip a query through this connection at all." That's genuinely different from checking "is the TCP port open" — a database can accept connections while refusing queries (out of connections, out of disk, mid-failover).

Notice what doesn't happen on failure: no exception escapes check_db(). A health check that crashes with a 500 on the one dependency that's actually down is worse than useless — it hides the truth ("db is down") behind a different truth ("the health check itself is broken").

This is a real design principle, not specific to this project: monitoring code should fail soft. Catch, report, move on.

Three checks, three different kinds of "alive"

Each check answers a differently-shaped question, because each dependency fails differently:

  • Database — binary. A query either round-trips or it doesn't (ok / error).
  • Redis — also binary, via await client.ping(), redis-py's own liveness call.
  • Worker — not binary. There's no direct question to ask a process with no server (lesson 4 covers why). Instead: read the timestamp it last wrote, and reason about its age.

backend/src/ticker_backend/health.py

WORKER_STALE_AFTER_SECONDS = 30

async def check_worker(client: Redis | None) -> dict:
    raw = await client.get(WORKER_HEARTBEAT_KEY)
    if raw is None:
        return {"status": "error", "detail": "no heartbeat recorded yet"}

    age_seconds = round(time.time() - float(raw), 1)
    if age_seconds > WORKER_STALE_AFTER_SECONDS:
        return {"status": "stale", "age_seconds": age_seconds}
    return {"status": "ok", "age_seconds": age_seconds}

Three possible worker states, not two: error (never checked in — maybe it never started), stale (checked in once, but not recently — maybe it's wedged or crashed mid-loop), and ok (checked in recently). 30 seconds against a 5-second heartbeat interval (lesson 4) is deliberate slack — one or two missed beats shouldn't flip the status page red.

A simplification worth naming, not hiding

check_redis() opens a brand-new Redis connection on every single call to /health, then closes it a few lines later: 

async def check_redis() -> tuple[dict, Redis | None]:
    client = Redis.from_url(settings.redis_url)
    try:
        await client.ping()
        return {"status": "ok"}, client
    ...

A production system would keep one shared, pooled client alive for the app's whole lifetime instead of opening a fresh connection per request — cheaper, and it's what _engine above already does correctly for the database (an engine manages its own connection pool). This is the honest exception: fine for a health check hit once every five seconds, worth flagging as the thing to fix if this pattern ever spreads to a real, frequently-called endpoint.

The aggregation itself: sequential, on purpose

@router.get("/health")
async def health() -> dict:
    db_status = await check_db()
    redis_status, redis_client = await check_redis()
    worker_status = await check_worker(redis_client)
    ...
    return {"api": ..., "db": db_status, "redis": redis_status, "worker": worker_status}

Three awaits in a row means three round trips in sequence, not in parallel — asyncio.gather() could run them concurrently and shave a few milliseconds off. For an endpoint polled every 5 seconds by one browser tab, that's not a real cost; the simpler, more obviously-correct code won here. Worth knowing gather exists for the day this endpoint's checks get slower or more numerous.

Check your understanding

Q1. The worker process crashes. Redis and Postgres are both fine. What does /health report for worker, and roughly how long after the crash?

Reveal answer

stale once the heartbeat key is more than 30 seconds old (up to ~35s after the crash, worst case) — not immediately, and not error, since a heartbeat was written before.

Q2. Why does check_db() catch Exception and return a dict instead of letting FastAPI turn a database error into a 500 response?

Reveal answer

A 500 on /health would only tell you the health check itself broke — not which dependency is actually down. Catching and reporting per-check is what lets one bad dependency show up as one red tile instead of taking the whole endpoint down.
