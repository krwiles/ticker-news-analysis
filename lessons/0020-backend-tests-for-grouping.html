Backend tests for grouping

A fake that computes real cosine similarity, a failure path that had to be built before it could be tested, and one more DI gap lesson 19 left behind.

Mirrors lesson 10's shape: pure logic, mocked integration tests, explicit failure paths, and a final step that deliberately breaks something real to prove the tests actually catch it.

Step zero: the refactor comes before the tests, not with them

Lesson 19's Milvus calls reached a global get_milvus_client() internally — the one place in this grouping code that wasn't parameter-injected the way everything else already is. Before writing a single test, that got fixed in isolation: milvus=None added to every function that touches Milvus, defaulting to the real client. Then, before moving on, all three of lesson 19's own live-verification scripts got re-run against the real stack — not just the existing `pytest` suite — to confirm byte-for-byte identical behavior. Only after that came back clean did any lesson 20 code get written.

A fake that computes real cosine similarity, not canned answers

respx can mock OpenAI because OpenAI is plain HTTP. Milvus talks gRPC — nothing `respx` touches. The fix isn't a dumb stub that just returns a fixed response regardless of input; it's a small in-memory store with a real similarity search: 

def search(self, collection_name, data, filter, limit, **kwargs):
    ticker, day = _parse_ticker_day_filter(filter)
    query = data[0]
    candidates = [row for row in self.rows if row["ticker"] == ticker and row["day"] == day]
    scored = sorted(
        ({"story_id": row["story_id"], "distance": _cosine_similarity(query, row["embedding"]), "entity": {}}
         for row in candidates),
        key=lambda hit: hit["distance"], reverse=True,
    )
    return [scored[:limit]]

This matters because the thing worth testing isn't "was search() called" — it's "did the code make the right matching decision." A fake that just returns a fixed hit would pass every test regardless of whether the real threshold logic worked at all. This one actually computes similarity, so a genuinely wrong threshold comparison makes a real test fail — proven directly, not assumed (see the verification section below).

Worth being honest about what this fake can't do: it's a Python dict, always perfectly consistent. It can't regression-test Milvus's real consistency_level="Strong" behavior — that's an infrastructure fact, not application logic, and no fake substitutes for it. Lesson 19's own throwaway scripts stay around for that, checked manually, not folded into this suite.

The failure path had to be built before it could be tested

Writing this lesson's failure-path tests surfaced a real inconsistency lesson 19 shipped with: no OPENAI_API_KEY configured skipped grouping gracefully, but a configured key that's temporarily unreachable propagated and failed the whole job — even though headlines were already safely persisted. Fixed before any test for it existed:

except (ProviderFetchError, MilvusException) as exc:

Both cases now degrade gracefully — headlines always persist — but stay distinguishable through a new grouping field ("ok" / "skipped" / "error") that flows from _assign_stories through the job result into /api/search's own JSON response. Verified live before being written up as a mocked test: a real invalid API key against OpenAI's real endpoint produced a real 401, caught cleanly, logged, returned "error", headline still persisted — the exact behavior the test below asserts, proven against reality first.

One deliberate design choice worth naming: filings commit in their own transaction, separate from news-matching. A Milvus outage midway through matching rolls back that attempt's news assignments — but never touches filings, which don't depend on Milvus at all. Discarding already-successful, independent work just because something unrelated failed later would be a worse outcome than the failure itself.

A gap found only once the tests demanded it

The permanence test needed to call the real fetch_and_persist_headlines orchestrator (not _assign_stories directly — that's the whole point, proving the caller's new-vs-known logic, not just the grouping function in isolation) with a fake Milvus injected. That function didn't have anywhere to inject one at all — only _assign_stories, one level down, did. Same fix as step zero, one level higher: milvus=None added to fetch_and_persist_headlines too, threaded straight through. A small, mechanical gap — but one the plan hadn't anticipated, only test-writing surfaced it.

backend/tests/test_grouping.py

embeddings_route = respx.post("https://api.openai.com/v1/embeddings").mock(...)
first = await fetch_and_persist_headlines("GOOG", session_factory=test_session_factory, milvus=fake)

assert embeddings_route.call_count == 1  # the second run must never re-embed an already-known headline

Checking the mock's own call count, not just that the outcome looks unchanged, is the stronger assertion — it proves the already-known headline was never even handed to grouping a second time, not just that grouping happened to produce the same answer twice.

Verification: break something real, watch the right tests fail

Same discipline lesson 10 established. The threshold comparison got commented out (if False and hits and ...) and the suite re-run: exactly the two match-dependent tests failed — the same-event grouping test and the late-match test — every non-matching test (different ticker, different day, genuinely different content) stayed green, because they were never relying on a match succeeding in the first place. Reverted; 33/33 clean again.

Check your understanding

Q1. Why does the fake Milvus client compute real cosine similarity instead of just returning a fixed, pre-decided hit?

Reveal answer

A fixed response would only prove the code called search() -- it wouldn't prove the matching *decision* (compare the score against the threshold, match or found a new Story) is actually correct. A fake that computes a real score makes a genuinely broken threshold comparison fail a real test, which is exactly what the verification step at the end demonstrated directly, not just assumed.

Q2. Why do filings commit in their own transaction, separate from news-matching, rather than all being part of one shared session?

Reveal answer

Filings never depend on OpenAI or Milvus at all -- they always succeed. If they shared one transaction with news-matching and a Milvus failure happened partway through the news loop, the whole transaction (including the filing work that had nothing to do with the failure) would roll back too. Committing them separately means a later, unrelated failure can never discard already-successful, independent work.

Q3. The permanence test asserts embeddings_route.call_count == 1 after two runs. Why is that a stronger check than just asserting the two runs produced the same story_id?

Reveal answer

Asserting the same story_id only proves the *outcome* looks unchanged -- it wouldn't catch a bug where the code re-embeds and re-matches the headline on the second run but happens to land on the same answer both times, by chance or because there's nothing else for it to match against. Asserting the call count proves the already-known headline was never even handed to grouping a second time, which is the actual permanence guarantee spec 0002 describes.
