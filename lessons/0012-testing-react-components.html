Testing React components

Vitest + Testing Library, and two real bugs the first test run caught before you did.

Inserted after lesson 11 specifically to resolve something ADR 0005 deliberately left open: "frontend testing tooling remains an open decision, to be made when the React lessons actually begin." That's now. Tests all four of lesson 11's new files — SearchBar, HeadlineList, search.ts, SearchPage — 20 tests, all passing.

The tool: Vitest, not Jest — and why that's not arbitrary

tsconfig.json is already fully modern-ESM ("module": "ESNext", "moduleResolution": "bundler"). Jest's ESM support still needs an extra transform layer (ts-jest or babel-jest) to avoid CJS/ESM friction; Vitest handles it natively — no new transform config, and no new plugin for JSX either (its built-in esbuild transform handles .tsx out of the box). Vitest doesn't touch webpack.config.js at all — it's a standalone test runner, the same relationship pytest has to uvicorn.

Two layers of mocking — the same two-layer shape lesson 10 used

The backend's test suite has a real, worth-repeating shape:

Backend (lesson 10) Frontend (this lesson)
respx mocks real httpx calls vi.stubGlobal("fetch", ...) in search.test.ts
app.dependency_overrides[get_arq_redis] vi.mock("../search") in SearchPage.test.tsx

Worth being precise about the contrast this reveals, tying back to lesson 11's DI discussion ([[di-mechanism-follows-two-independent-questions]]): the backend's testability comes from parameter injection — session_factory is a real argument, swapped by passing a different one. vi.mock("../search") achieves the same goal a completely different way — it replaces the entire imported module at the boundary, without SearchPage.tsx itself needing any parameter for it. Same destination (a swappable test double at the seam), different mechanism — because the ecosystem's idioms differ, not because one approach is more correct.

Bug #1, found on the first real test run: state leaking between tests

HeadlineList.test.tsx's "omits outlet text when null" test failed — but the element it found had via Yahoo in it, from the previous test. React Testing Library only self-registers automatic cleanup between tests when it detects a global afterEach — and this project deliberately keeps test.globals off (test files import describe/it/expect explicitly from "vitest" rather than relying on injected globals). Without a global to hook into, nothing ever unmounted the previous render. Fixed explicitly in vitest.setup.ts: 

import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(() => {
  cleanup();
});

Keeps the "no injected globals" decision intact, rather than flipping on globals: true to make the automatic detection work.

Bug #2: a setup file living outside tsconfig.json's own include

npm run test was green — but npm run typecheck failed everywhere, with errors like Property 'toBeInTheDocument' does not exist. The matcher works at runtime (@testing-library/jest-dom/vitest registers it against the real expect), but its type declaration only gets loaded if TypeScript actually parses the file that imports it. vitest.setup.ts lived at the repo root; tsconfig.json's "include": ["src"] never looked there — so tsc silently never saw the augmentation. Fixed by moving the setup file to src/vitest.setup.ts, not by adding a new tsconfig types entry — the smaller, more localized fix.

Check your understanding

Q1. Why did HeadlineList's "omits outlet" test see a leftover element from an earlier test, and why doesn't setting test.globals: true get chosen as the fix here?

Reveal answer

Testing Library's automatic cleanup only self-registers by detecting a global afterEach; this project deliberately doesn't inject globals, so nothing ever unmounted the previous render. globals: true would fix it too, but at the cost of the explicit-imports decision this project made on purpose — an explicit afterEach(cleanup) in the setup file fixes the actual problem without touching that decision.

Q2. search.test.ts and SearchPage.test.tsx both "mock the network," but at different layers. What's the actual difference?

Reveal answer

search.test.ts stubs the raw fetch global -- it's testing fetchSearch itself, the thing that talks to the network. SearchPage.test.tsx mocks the entire search.ts module -- it's testing a consumer of fetchSearch, which shouldn't care how the network call is made, only what it returns. Same shape as respx (mocks the HTTP layer) vs. dependency_overrides (mocks one layer up, at the endpoint's own boundary) on the backend.
