A naming collision that was easy to miss

The response already has a top-level "sentiment" key — added in lesson 26, a status string: ok/skipped/error/processing. This lesson needs a different kind of value per headline and per Story: the classification itself, positive/neutral/negative. Reusing the bare name sentiment at a nested level would mean the exact same key holds two totally unrelated value domains depending on how deep you're reading into the JSON — precisely the kind of trap CONTEXT.md's own collision warnings exist to catch (it already flags "sentiment category" for colliding with category). Settled on sentiment_enum instead, matching the sentiment_score/ sentiment_gloss/sentiment_rationale/sentiment_status naming already in place.

The real gap: a Story dict never had a Story row to read from

_group_into_stories only ever received Headline objects — it builds a Story's shape (primary + other members) purely by grouping headlines on their shared story_id. It never needed the actual stories row itself, because nothing about primary/member selection depends on it (ADR 0009: primary is derived from published_at, not stored). The aggregate breaks that — sentiment_average lives on the real Story row, not anywhere in its Headlines. A second, plain query (not an ORM relationship — this codebase's existing convention) builds a lookup dict, threaded through as a new parameter: 

def _group_into_stories(headlines: list[Headline], stories_by_id: dict) -> list[dict]:
    ...
    story = stories_by_id.get(primary.story_id)
    has_aggregate = story is not None and story.sentiment_score_count > 0
    ...
    "sentiment_average": story.sentiment_average if has_aggregate else None,
    "sentiment_enum": derive_sentiment_enum(story.sentiment_average) if has_aggregate else None,

Always present, always nullable — never conditionally left out of the dict. The frontend already has its own reason to check member count (whether to show the "+N more sources" disclosure at all); it doesn't need the backend to encode that same decision a second time by omitting keys.

Verified against real, live data — not just the mocked tests

A real single-member MSFT Story: sentiment_average: 60.0, matching its one member's own score exactly — confirms a "Story of one" still gets a real aggregate at the data level, even though the frontend (lesson 29) won't render it as one. A real 3-member Story: sentiment_average: 80.67, matching (85 + 82 + 75) / 3 exactly — the same incremental-average math from lesson 26, now read back correctly through a completely independent code path (the API response, not the job that wrote it).

Check your understanding

Q1. Why not just call the new per-headline field "sentiment", matching CONTEXT.md's own term for the concept?

Reveal answer

The response's top-level "sentiment" key already exists, and it's a different kind of value entirely (a status: ok/skipped/error/processing). Reusing the name at a nested level would mean the same key means two unrelated things depending on how deep you're reading -- exactly the collision CONTEXT.md's own _Avoid_ notes exist to prevent. "sentiment_enum" keeps the concept clear and matches the naming pattern the other four fields already use.

Q2. Why does a "Story of one" (no other_members) still get a non-null sentiment_average in the API response?

Reveal answer

The backend doesn't know or care about the "should the UI show an aggregate card" decision -- that's the frontend's own job, based on member count, which it already needs to check for the "+N more sources" disclosure. The backend's job is just to report the real, true state: sentiment_score_count was incremented once, so there's a real (if single-member) average to report. Hiding it here would just be re-deciding something the frontend is already equipped to decide.
