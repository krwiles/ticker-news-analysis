The stories table + migration

Schema before logic, same shape as lesson 6 — and a design that got genuinely simpler under review, kept in the lesson rather than smoothed over.

No matching logic yet — that's lesson 19. This lesson is purely stories + headlines.story_id, the same "schema first" shape lesson 6 used for Headline itself. What follows is the actual design history, not just the final answer — the first version shipped, passed its tests, and then got replaced before it ever merged.

Version one: a circular FK, reasoned through carefully

A Story needs to know its "primary" headline — the one displayed in full, per spec 0002. The first design stored that directly: stories.primary_headline_id, a real FK into headlines.id. That immediately raises an ordering problem worth sitting with: a stories row has to exist before the headline that becomes its primary — that headline needs a valid story_id to reference, so the story has to exist first. Which means primary_headline_id can't be set at creation time; it has to start null and get backfilled in a second write, once the headline actually exists: 

# 1. story exists, no primary yet
story = Story(ticker="AAPL")
await session.commit()

# 2. the headline can now reference it
headline = Headline(..., story_id=story.id)
await session.commit()

# 3. backfill
story.primary_headline_id = headline.id
await session.commit()

This is a real, recognized database pattern — a mutual/circular FK with a permanently-nullable back-pointer, the same shape as a textbook Company.ceo_id ↔ Employee.company_id relationship. Not wrong. It shipped, it had a passing test proving the three-step sequence worked. And it was more machinery than the problem actually needed.

The question that undid it: is any of this fact actually new information?

A Story's primary is always its earliest-published member — settled back in the grilling round, never up for debate. That means primary-ness is a pure function of data Headline already has: story_id grouped, published_at ordered. Storing primary_headline_id separately doesn't encode any new fact — it duplicates one that's already fully determined, in a form that could theoretically drift out of sync with the source of truth, for a guarantee (fast lookup) an index gets you just as well without the duplication.

A middle option got considered and rejected too: a headlines.is_primary boolean flag instead of a back-pointer — avoids the circular FK, but is still the same redundant fact in a different shape, still needs a partial unique index to enforce "at most one per story," and still needs deciding and setting at write time. Neither version earns its keep once you notice the fact doesn't need storing at all.

Version two: derive it, store nothing

SELECT * FROM headlines
WHERE story_id = X
ORDER BY published_at ASC
LIMIT 1;

Backed by a composite index on (story_id, published_at) — an index-scan lookup, not a table scan, genuinely cheap. For rendering a whole day's worth of Stories at once, the natural SQL is a window function (ROW_NUMBER() OVER (PARTITION BY story_id ORDER BY published_at)) — exactly as easy to write with this design as it would have been with a stored flag, which is worth noticing: the flag never actually bought the query-ergonomics win it looked like it might.

Final shape: stories(id, ticker) — nothing else. headlines.story_id is the only cross-reference, one direction only. No circular FK, no permanently-nullable column to explain, no write-time decision about primary-ness at all.

Worth naming the general principle, not just this one instance: if a fact is fully derivable from data you already store, storing it again is redundant state — even when it feels convenient, even when there's a clean-looking column name for it. The cost isn't always obvious upfront (the circular-FK version worked, and was reasoned through carefully) — it shows up as complexity that had no real reason to exist once you ask "does this column encode anything new?"

A second, unrelated bug: the test cleanup fixture didn't know about the new table

Separately from the design change above — this one held true in both versions of the schema. The first real test run failed all 18 tests at once: 

sqlalchemy.exc.DBAPIError: cannot truncate a table referenced in a foreign key constraint
DETAIL: Table "stories" references "headlines".

conftest.py's cleanup fixture did TRUNCATE TABLE headlines, companies — written before stories existed, so it had no idea the new table was there. Postgres refuses to truncate a table something else has a live FK into, unless the referencing table is truncated in the same statement. Fixed by adding stories to that one line. The lesson here: going nullable was still the right call for story_id itself — no test needed new logic to satisfy a constraint — but "zero blast radius" was only half true. Shared test infrastructure still had to learn about the new table the moment it entered the FK graph.

Check your understanding

Q1. What was actually wrong with the circular-FK design — was it a bug?

Reveal answer

No bug -- it worked, and had a passing test proving the write sequence was correct. The problem was that it stored a fact (which headline is primary) that's fully derivable from data Headline already has (story_id + published_at), for no benefit an index-backed query couldn't provide just as well. Redundant state, not incorrect state.

Q2. Why does the new test insert headlines out of chronological order on purpose?

Reveal answer

To prove the query actually derives "primary" from published_at, not from insertion order. If the two happened to match (insert in chronological order), a bug that used insertion order instead of published_at could pass the test by accident -- inserting out of order is what makes the test a real proof of the correct rule, not just a coincidence.
