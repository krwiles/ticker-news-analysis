The stories table + migration

Schema before logic, same shape as lesson 6 — and a deliberate deviation from what the architecture docs say, made explicit rather than silently ignored.

No matching logic yet — that's lesson 19. This lesson is purely stories + headlines.story_id, the same "schema first" shape lesson 6 used for Headline itself. See ADR 0009 for the full "why a real table, not a bare column" reasoning — this lesson is about building it, and one place it deliberately doesn't match that ADR yet.

A deliberate deviation from the architecture doc, made explicit

ADR 0009 describes headlines.story_id as eventually NOT NULL — "every headline gets one, even a Story of one." Taken literally, right now, that would break something real: providers.py's existing insert path has no matching logic yet to decide a story for anything, and several existing tests insert headlines directly. Making it NOT NULL today would mean either writing throwaway placeholder logic just to satisfy a constraint, or breaking the app outright.

Decision: nullable now, tightened once lesson 19's real matching logic exists to populate it on every path — the same staged-rollout pattern outlet/summary already used (added in a later migration, not day one). Worth being honest that this is a real deviation from what ADR 0009 describes as the eventual design, not a contradiction of it — and it's exactly why that ADR explicitly left this specific sequencing question open rather than settling it itself.

The one thing that truly can't be staged: primary_headline_id

stories.primary_headline_id is nullable permanently, not as a rollout choice. A stories row has to be written before the headline it will eventually call primary — that headline needs a valid story_id to reference, which means the story has to exist first. So primary_headline_id necessarily starts null and gets backfilled in a second write: 

# 1. story exists, no primary yet
story = Story(ticker="AAPL")
session.add(story)
await session.commit()

# 2. the headline can now reference it
headline = Headline(..., story_id=story.id)
session.add(headline)
await session.commit()

# 3. backfill
story.primary_headline_id = headline.id
await session.commit()

A circular FK relationship, both directions real: headlines.story_id → stories.id and stories.primary_headline_id → headlines.id. The migration has to create both tables/columns before adding either constraint, for the same reason — each references something that has to already exist.

A real bug: the nullable decision didn't fully deliver on its own promise

The whole point of going nullable was "zero changes to existing tests." The first real test run said otherwise — all 18 tests failed, not from the new column, but from conftest.py's own cleanup fixture: 

sqlalchemy.exc.DBAPIError: cannot truncate a table referenced in a foreign key constraint
DETAIL: Table "stories" references "headlines".

TRUNCATE TABLE headlines, companies — the fixture that resets state before every test — had no idea stories existed. Postgres refuses to truncate a table something else has a live FK into, unless the referencing table is truncated in the very same statement. Fixed by adding stories to that one line. Worth sitting with precisely: the nullable-column decision was still the right call — no test needed new logic to satisfy a constraint — but "zero blast radius" was only half true. Shared test *infrastructure* still had to learn about the new table the moment it entered the FK graph, independent of whether any column was nullable.

Q1. Why is headlines.story_id nullable right now, when ADR 0009 describes it as eventually NOT NULL?

Reveal answer

No matching logic exists yet (that's lesson 19) to decide a story for every incoming headline, and providers.py's existing insert path -- plus several existing tests -- would break if the column required a value nothing yet supplies. Nullable now, tightened once lesson 19 can actually populate it on every path -- the same staged-rollout pattern outlet/summary already used.

Q2. Why can't stories.primary_headline_id ever be NOT NULL, even after lesson 19 ships?

Reveal answer

A stories row is necessarily written before the headline that becomes its primary -- that headline needs a valid story_id to reference, so the story has to exist first. At the moment a new Story is created, its primary headline doesn't exist yet, so primary_headline_id has to start null and get backfilled in a second write. A structural consequence of the circular FK, not a rollout stage.
