OpenAI embeddings integration

A fourth provider call, in a shape you've now written three times before — and the lesson where an ADR named a function before it existed.

No Milvus wiring yet, no fetch_and_persist_headlines changes — that's lesson 19. This lesson only proves one thing: a real call to OpenAI's embeddings API, in providers.py, following the exact shape get_company/fetch_edgar_filings/fetch_finnhub_news already established.

An ADR that named this function before it existed

While planning this lesson, a question surfaced that had never been asked out loud before: should get_embedding use OpenAI's official openai Python package, or stay on raw httpx like every provider call so far? EDGAR has no SDK at all, so fetch_edgar_filings never had a choice — but Finnhub and OpenAI both have official clients, and this project had just never written down why it wasn't using them.

The answer became ADR 0010, and it's worth reading closely for one detail: it lists get_embedding as an existing example of the shared provider shape — written before the function itself was built. That's the ADR discipline this project has been practicing since spec 0002 (see learning-records/0007): settle the architectural question in writing first, then implement against it, not the other way around.

The function itself

backend/src/ticker_backend/providers.py

OPENAI_EMBEDDING_MODEL = "text-embedding-3-small"


async def get_embedding(text: str, client: httpx.AsyncClient) -> list[float]:
    try:
        response = await client.post(
            "https://api.openai.com/v1/embeddings",
            headers={"Authorization": f"Bearer {settings.openai_api_key}"},
            json={"model": OPENAI_EMBEDDING_MODEL, "input": text},
        )
        response.raise_for_status()
        body = response.json()
    except (httpx.HTTPError, ValueError) as exc:
        raise ProviderFetchError(f"OpenAI embedding fetch failed: {exc}") from exc

    try:
        return body["data"][0]["embedding"]
    except (KeyError, IndexError) as exc:
        raise ProviderFetchError(f"OpenAI embedding response missing data: {exc}") from exc

Compare this against fetch_finnhub_news and the shape is identical on purpose: an httpx.AsyncClient passed in (never created here — the caller owns connection lifetime, same reasoning as every other provider function), a typed ProviderFetchError on any failure, no provider-specific SDK object anywhere. The only real difference from Finnhub's call is the second try/except — OpenAI's success response is nested one level deeper (data[0].embedding) than Finnhub's flat array, so there are two distinct ways this call can fail: the HTTP request itself, or a 200 response whose body doesn't have the shape expected.

Two decisions ADR 0007 left open

ADR 0007 settled the technology (OpenAI over Cohere or a local model) months before this lesson, but two real choices were still open going into it, both closed during this lesson's planning pass:

  • Which model. text-embedding-3-small — OpenAI's cheapest tier, matching ADR 0007's own cost estimate, and its dimension count (1536) is what milvus_client.py's own docstring had been waiting on: "no collection schema for real headline embeddings lives here yet — that depends on OpenAI's embedding dimension, not chosen until lesson 18." That dependency is resolved now, live-verified below.
  • What text to embed. ADR 0007 said "title + summary, when present" but never specified the join. Pulled into its own small, pure function so the decision is independently testable, not buried inside get_embedding itself: 
    def embedding_input_text(title: str, summary: str | None) -> str:
    if summary is None:
        return title
    return f"{title}\n\n{summary}"
    Same instinct as search.py's split_today_recent: extract the part with real decision logic into something you can call directly from a test, rather than asserting on it indirectly through the bigger function's behavior.

Live verification: what actually happened

Same discipline lessons 7 and 8 established for EDGAR/Finnhub — mocked tests prove the code handles known shapes correctly, but only a real call proves the assumed shape is the actual shape. One real request, using a real headline's title and summary: 

embedding length (dimensions): 1536
elapsed: 2.23s (job_timeout_seconds budget: 10s)

Three things confirmed, none of them assumed in advance: the response really does nest the vector at data[0].embedding exactly as coded; the model really does produce 1536 numbers, settling the Milvus dimension question for lesson 19; and — closing an uncertainty ADR 0007 named explicitly ("worth verifying live once real embedding latency exists to measure, not assumed fine in advance") — a single call costs about 2 seconds, well inside the 10-second job_timeout_seconds budget the fetch job already runs under.

That last number comes with a caveat worth carrying into lesson 19: 2.23s was measured for one isolated call. Once this runs inside the real fetch job — potentially once per new headline, alongside EDGAR and Finnhub in the same asyncio.gather — the real question becomes total time across however many headlines a single search turns up, not the cost of one call in isolation.

Check your understanding

Q1. get_embedding has two separate try/except blocks, not one. What distinct failure does each one guard against?

Reveal answer

The first guards the HTTP call itself -- a network error, a timeout, or a non-2xx status (a bad API key, a rate limit, a server error). The second guards a *successful* 200 response whose JSON body doesn't have the expected data[0].embedding shape -- a different failure mode entirely, worth its own typed error and its own message, rather than letting a raw KeyError leak out uncaught.

Q2. Why does embedding_input_text exist as its own top-level function instead of being three lines inline inside get_embedding?

Reveal answer

It's the one piece of this lesson with genuine decision logic -- how to join title and summary -- as opposed to get_embedding's mechanical HTTP-call-in, vector-out shape. Pulling it out means it can be tested directly (two tests, no-summary and with-summary) without needing a mocked HTTP call at all, the same reasoning search.py's split_today_recent already established for keeping pure decision logic separate from the I/O around it.
