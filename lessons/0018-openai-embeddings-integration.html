Lesson 18 of 18 · ticker-news-analysis stack (infra arc — Arc 4)

OpenAI embeddings integration

A fourth provider call, in a shape you've now written three times before — and the lesson where an ADR named a function before it existed.

No Milvus wiring yet, no fetch_and_persist_headlines changes — that's lesson 19. This lesson only proves one thing: a real call to OpenAI's embeddings API, in providers.py, following the exact shape get_company/fetch_edgar_filings/fetch_finnhub_news already established.

An ADR that named this function before it existed

While planning this lesson, a question surfaced that had never been asked out loud before: should the new embedding call use OpenAI's official openai Python package, or stay on raw httpx like every provider call so far? EDGAR has no SDK at all, so fetch_edgar_filings never had a choice — but Finnhub and OpenAI both have official clients, and this project had just never written down why it wasn't using them.

The answer became ADR 0010, and it's worth reading closely for one detail: it lists get_embeddings as an existing example of the shared provider shape — written before the function itself was built (originally under a different, singular name — see below). That's the ADR discipline this project has been practicing since spec 0002 (see learning-records/0007): settle the architectural question in writing first, then implement against it, not the other way around.

Version one: a single call per headline

The function that first proved OpenAI's endpoint worked took one headline's text in and returned one vector out — the same shape every other provider function uses. It worked, it was tested, and a real call against OpenAI confirmed the response shape (data[0].embedding) and a 1536-dimension result, settling the number milvus_client.py's own docstring had been waiting on since lesson 16.

That single real call also measured something worth sitting with: about 2 seconds of latency. Fine for one headline — but a real search can turn up tens of headlines in one fetch, and fetch_and_persist_headlines runs under a hard 10-second budget (job_timeout_seconds, ADR 0004). One call per headline, run serially, doesn't fit: 10 headlines at ~2s each is already past the budget on its own, before EDGAR or Finnhub even run.

The question that undid it: does this need to be N calls at all?

OpenAI's embeddings endpoint accepts input as a string or an array of strings — a detail easy to miss reading the single-call version in isolation, but obvious once the latency number made a per-headline loop look infeasible. Nothing about Story-matching (ADR 0006) requires embeddings to be fetched one at a time; only the comparison step is inherently sequential (each new headline checked against each existing Story's primary). The fetch step itself can be one request for every new headline a search turns up.

Version two: one batched request

backend/src/ticker_backend/providers.py

OPENAI_EMBEDDING_MODEL = "text-embedding-3-small"


async def get_embeddings(texts: list[str], client: httpx.AsyncClient) -> list[list[float]]:
    if not texts:
        return []

    try:
        response = await client.post(
            "https://api.openai.com/v1/embeddings",
            headers={"Authorization": f"Bearer {settings.openai_api_key}"},
            json={"model": OPENAI_EMBEDDING_MODEL, "input": texts},
        )
        response.raise_for_status()
        body = response.json()
    except (httpx.HTTPError, ValueError) as exc:
        raise ProviderFetchError(f"OpenAI embedding fetch failed: {exc}") from exc

    try:
        by_index = {item["index"]: item["embedding"] for item in body["data"]}
        return [by_index[i] for i in range(len(texts))]
    except (KeyError, IndexError) as exc:
        raise ProviderFetchError(f"OpenAI embedding response missing data: {exc}") from exc

Same provider shape as before — httpx.AsyncClient passed in, typed ProviderFetchError on failure, no SDK — plus two real additions. First, an empty-input guard: lesson 19 will call this once per fetch job run with however many new headlines that run found, which is often zero, and zero headlines shouldn't mean a wasted network call. Second, each vector is placed into the result by its own index field rather than trusted to come back in request order — cheap insurance against a batch API that doesn't document a strict ordering guarantee.

Two decisions ADR 0007 left open

ADR 0007 settled the technology (OpenAI over Cohere or a local model) months before this lesson, but two real choices were still open going into it, both closed during this lesson's planning pass:

  • Which model. text-embedding-3-small — OpenAI's cheapest tier, matching ADR 0007's own cost estimate, and its dimension count (1536) is what milvus_client.py's own docstring had been waiting on: "no collection schema for real headline embeddings lives here yet — that depends on OpenAI's embedding dimension, not chosen until lesson 18." That dependency is resolved now, live-verified below.
  • What text to embed. ADR 0007 said "title + summary, when present" but never specified the join. Pulled into its own small, pure function so the decision is independently testable, not buried inside get_embeddings itself: 
    def embedding_input_text(title: str, summary: str | None) -> str:
    if summary is None:
        return title
    return f"{title}\n\n{summary}"
    Same instinct as search.py's split_today_recent: extract the part with real decision logic into something you can call directly from a test, rather than asserting on it indirectly through the bigger function's behavior.

Live verification: does batching actually help?

The whole point of version two was a hypothesis — one batched request should cost roughly the same as one isolated call, regardless of how many headlines are in it, because the dominant cost is the network round-trip, not per-item compute. Tested directly against 10 realistic headlines, not assumed: 

single call (1 headline):     1.83s
batched call (10 headlines):  1.13s
naive serial estimate (10×):  18.32s
job_timeout_seconds budget:   10s

The batched call didn't just avoid scaling linearly — it came back faster than the single-headline baseline (ordinary request-to-request variance, not a real trend, but proof the batch endpoint isn't penalizing larger inputs). The naive serial estimate for the same 10 headlines — 18.32s — makes the original per-headline design's real cost concrete: it would have blown the entire job_timeout_seconds budget on embeddings alone, before EDGAR or Finnhub even ran. This closes the uncertainty ADR 0007 flagged explicitly ("worth verifying live once real embedding latency exists to measure, not assumed fine in advance") — see its own revised Consequences section for the full write-up.

Check your understanding

Q1. get_embeddings has two separate try/except blocks, not one. What distinct failure does each one guard against?

Reveal answer

The first guards the HTTP call itself -- a network error, a timeout, or a non-2xx status (a bad API key, a rate limit, a server error). The second guards a *successful* 200 response whose JSON body doesn't have the expected data[i].embedding shape for every item -- a different failure mode entirely, worth its own typed error and its own message, rather than letting a raw KeyError leak out uncaught.

Q2. Why does get_embeddings place each vector by its index field instead of just returning [item["embedding"] for item in body["data"]] in array order?

Reveal answer

Array order would only be correct if OpenAI's batch response is guaranteed to preserve request order -- a real assumption, not verified. Each response item already carries its own index field naming which input position it corresponds to, so placing by index costs almost nothing and removes the assumption entirely: correct even if a future response ever came back reordered.

Q3. Why does embedding_input_text exist as its own top-level function instead of being three lines inline inside get_embeddings?

Reveal answer

It's the one piece of this lesson with genuine decision logic -- how to join title and summary -- as opposed to get_embeddings' mechanical HTTP-call-in, vectors-out shape. Pulling it out means it can be tested directly (two tests, no-summary and with-summary) without needing a mocked HTTP call at all, the same reasoning search.py's split_today_recent already established for keeping pure decision logic separate from the I/O around it.
