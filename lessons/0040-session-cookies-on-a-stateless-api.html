Session cookies on a stateless API: how a REST endpoint knows who's asking

The question that stopped the watchlists design cold: "our endpoints are REST, doesn't that mean they're stateless? How can /api/search know I'm signed in?" This is the answer — general enough to carry into any REST API, then grounded in exactly how this app does it.

Stateless does not mean sessionless. It means the server keeps no memory of a client between requests. It says nothing about whether a request can carry identity — it says every request must carry everything the server needs, because the server won't remember it from last time. A cookie riding on every request is exactly that: identity the client brings, not state the server recalls.

What "stateless" actually says — from the source that coined it

REST's stateless constraint comes from Roy Fielding's 2000 dissertation, the original source every later description of REST ultimately traces back to. Its own words:

"Each request from client to server must contain all of the information necessary to understand the request, and cannot take advantage of any stored context on the server. Session state is therefore kept entirely on the client."

Read literally, that sounds like it rules out sessions entirely — "session state... kept entirely on the client" sounds like no server-side session store is allowed. But look at what the constraint is actually protecting against: a server that remembers something from request #1 and silently uses it to interpret request #2, without request #2 saying so itself. That's the failure mode statelessness exists to prevent — not "no identity," but "hidden, unstated context." A request that explicitly says "here is my session cookie, go look up what it means" states its own context in full. Nothing is hidden; nothing is assumed from a prior request. The server doing a fresh lookup on every single request, rather than remembering who you are from the last one, is the stateless behavior — not a violation of it.

How this app actually does it

ADR 0016 picked a server-side session store over the other common option (a self-contained signed token, e.g. a JWT) — and the reason is worth sitting with, because it's the actual trade-off every REST API authentication scheme makes:

"A signed cookie needs no server-side storage but can never be revoked early — the only lever is rotating the signing secret, which logs out everyone at once. Redis is already running here for ARQ; a session lookup is one cheap Redis round-trip, and it buys real per-session revocation."

A signed JWT is the purer expression of Fielding's ideal: the token itself carries everything (who you are, when it expires, a signature proving nobody tampered with it), so the server needs zero storage to trust it. But that purity has a cost — a valid-looking signature stays valid until it expires, full stop. Revoking one early means maintaining a server-side blocklist, which quietly reintroduces the exact server-side state a "stateless token" was supposed to avoid. This app instead stores an opaque, meaningless session ID in the cookie and keeps the meaning in Redis — a `session:{id}` key pointing at the signed-in user's `sub`, with a sliding TTL refreshed on every authenticated request: 

async def _resolve_session(redis, session_id: str) -> str | None:
    sub = await redis.get(f"session:{session_id}")
    if sub is None:
        return None
    await redis.expire(f"session:{session_id}", SESSION_TTL_SECONDS)  # sliding window
    return sub.decode() if isinstance(sub, bytes) else sub

Every one of this app's authenticated requests pays the cost of exactly one Redis GET — that's the whole price of "stateless," done right: cheap, explicit, and never dependent on the server remembering anything from a previous request.

Why a cross-origin fetch needs credentials: "include"

This app's UI (localhost:3000) and API (localhost:8000) are different origins (ADR 0002) — but the same site, since SameSite's definition ignores port entirely. Those are two separate concepts a fetch call has to satisfy, not one:

  • Site governs whether the cookie is sent at all under its SameSite attribute — same-site here, so SameSite=Lax already permits it.
  • Origin governs whether the browser's fetch() call itself is even allowed to attach cookies, independent of the cookie's own attributes. Per the Fetch spec's own default, fetch()'s credentials option defaults to "same-origin" — cookies ride along for same-origin requests automatically, but a cross-origin call sends none unless the caller explicitly opts in with credentials: "include".

So even though the cookie itself is perfectly willing to travel (same-site), the browser still won't attach it to a cross-origin request unless asked. That's why frontend/src/auth.ts passes credentials: "include" explicitly on every call — and why, on the server side, main.py's CORS config has to answer in kind with allow_credentials=True and a specific origin (never a wildcard — browsers refuse credentialed requests to *). Both sides have to agree, or the cookie never makes the trip in either direction.

Hands-on: two dependencies, not one

Watchlists (ADR 0019, built right after this lesson was requested) needed "who's signed in" in two genuinely different shapes. Four endpoints (add/remove/list a watchlist entry) must outright refuse a signed-out caller. But /api/search wanted to optionally record a view for a signed-in visitor, without ever blocking an anonymous one — this app's search has always worked for everyone, watchlists or not. One dependency can't do both, so this ADR factors the existing /api/auth/me lookup into two: 

async def require_user(request, session_factory, arq_redis) -> User:
    """401s if there's no valid session -- for endpoints that need a signed-in caller."""
    ...

async def optional_user(request, session_factory, arq_redis) -> User | None:
    """None if there's no valid session, never raises -- for callers that work either way."""
    ...

Both do the exact same stateless-per-request lookup underneath — read the cookie, ask Redis, done. The only difference is what happens when that lookup comes back empty: one treats it as an error, the other treats it as a perfectly normal, expected outcome. That split — same lookup, different failure handling — generalizes to any REST API with both "must be signed in" and "better if signed in" endpoints side by side.
