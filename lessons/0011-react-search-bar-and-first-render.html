React fundamentals, from Angular

A real search bar, wired to lesson 9's live endpoint — components, JSX, and hooks, mapped straight from what you already know.

The backend side of spec 0001 (docs/specs/0001-first-feature.md) has been done and tested since lesson 10. This lesson is the first one that builds anything on the frontend — App.tsx had exactly one route (StatusPage) before today. Two things are deliberately simplified here, confirmed rather than assumed — see the last section below.

Function components: no module system needed

SearchBar, HeadlineList, and SearchPage — all three new files this lesson — are just functions that return JSX. No decorator, no registration step:

frontend/src/components/SearchBar.tsx
export function SearchBar({ onSearch, disabled }: SearchBarProps) {
  const [ticker, setTicker] = useState("");
  // ...
  return (<form onSubmit={handleSubmit}>...</form>);
}

Angular's standalone @Component still needs a decorator and an imports array even without NgModules. React drops that layer entirely — a component is the function; you use it by calling it in JSX, the same as any other function.

useState: the same explicit reactive primitive as signal()

SearchBar's input is the direct translation-table example (NOTES.md): 

// Angular
ticker = signal("");
// read:  ticker()
// write: ticker.set(event.target.value)

// React (SearchBar.tsx)
const [ticker, setTicker] = useState("");
// read:  ticker
// write: setTicker(event.target.value)

Both are explicit, read/write reactive values — no implicit magic, no auto-tracked property access. The one real difference: a signal read (ticker()) is fine-grained — only the specific DOM binding that reads it updates. A useState read re-renders the whole component function that called the hook, every time. React's mental model is "the function reruns," not "this one expression updates."

Worth sitting with — the translation table's signal()↔useState() row is accurate at the surface, but this granularity gap is real, not a technicality.

JSX is just JavaScript — no template syntax

HeadlineList.tsx has both patterns the translation table names:

// Angular: @if / @for in a template
// React: plain JS inside JSX

if (headlines.length === 0) {
  return <p>No headlines in the past week for this ticker.</p>;
}

return (
  <ul>
    {headlines.map((headline) => (
      <li key={headline.url}>
        ...
        {headline.summary && <p>{headline.summary}</p>}
      </li>
    ))}
  </ul>
);

@for (headline of headlines) becomes a plain .map(); @if becomes either an early return or a && short-circuit. There's no separate syntax to learn here — the mental shift is that JSX has no template language of its own.

Two shapes of data fetching: effect-driven vs. event-driven

StatusPage.tsx (lesson 3) already fetches with useEffect — on mount, then again every 5 seconds, on its own schedule. SearchPage.tsx fetches differently: only when the form is submitted.

frontend/src/pages/SearchPage.tsx
async function handleSearch(ticker: string) {
  setLoading(true);
  setError(null);
  try {
    const result = await fetchSearch(ticker);
    setResults(result);
  } catch (err) {
    setError(err instanceof Error ? err.message : "unknown error");
  } finally {
    setLoading(false);
  }
}

No useEffect at all. In Angular terms, StatusPage's polling is closer to an effect() — something that reruns on its own whenever its schedule fires. handleSearch is closer to a plain method bound to (ngSubmit) — it runs exactly once, because something the user did called it directly. Not every async operation in a React component needs useEffect; reach for it specifically when something needs to happen in reaction to a render or a value changing, not whenever you need to fetch data at all.

This is also the first request the frontend makes that's genuinely slow. /health answers almost instantly; /api/search enqueues and awaits an ARQ job first (lesson 9, ADR 0004) — up to job_timeout_seconds (10s) before falling back. The loading state above isn't decoration — search a real ticker and watch it matter.

What's deliberately simplified today — and why

Two things, confirmed rather than assumed while planning this lesson:

  • One combined list, not Today/Recent. /api/search already returns separate today/recent arrays (spec 0001's real contract) — SearchPage.tsx just concatenates them ([...results.today, ...results.recent]). Splitting them into two headed lists with a real category badge (not plain text, which is what you see today) is lesson 14's job — the arc-2 capstone.
  • A second route, added but not explained. App.tsx now has /search alongside / — mechanically identical to the route that was already there, no new React Router concepts used. Lesson 13 is where routing itself becomes the actual subject.

Search a real, actively traded ticker and confirm it matches what lesson 9's curl calls showed. Check your understanding

Q1. Why doesn't SearchPage.tsx use useEffect to fetch, the way StatusPage.tsx does?

Reveal answer

StatusPage needs to fetch repeatedly on its own schedule (on mount, then every 5s) — that's exactly what useEffect is for. SearchPage's fetch only ever needs to happen in direct response to one thing: the user submitting the form. That's a plain event handler calling an async function directly — introducing useEffect here would be solving a problem (reacting to a value changing) this component doesn't actually have.

Q2. useState and Angular's signal() are both described as "explicit, read/write reactive values." What's the real difference this lesson names between them?

Reveal answer

Granularity. Reading a signal in a template updates only that specific binding. Reading state via useState means the entire component function reruns on every change — React re-renders whole components, not individual expressions.
