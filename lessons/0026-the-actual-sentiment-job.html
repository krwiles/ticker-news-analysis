Lesson 26 of 30 · ticker-news-analysis stack (sentiment arc — Arc 5)

The actual sentiment job

Two real architectural gaps found before any code was written, and a third found only once this ran against a real 239-headline batch — capstone of Arc 5, same role lesson 19 played for Arc 4.

Everything from lessons 23-25 gets wired together here: the columns, the classification call, the filing extraction. Two design gaps surfaced during planning, before a line of code existed. A third only showed up once this ran against real production volume, not a small sample.

Gap 1: "poll the same endpoint" quietly meant "re-fetch everything, every few seconds"

ADR 0014's original job-architecture decision said the frontend should poll the existing full /api/search-shaped response. Taken literally, that's wrong: /api/search unconditionally enqueues and awaits fetch_headlines_job on every call — polling it would re-trigger a full EDGAR/Finnhub/embeddings/grouping pass on every tick, not just re-check sentiment.

Fixed with a new, read-only GET /api/search/status — no job enqueue at all, just current Postgres state, sharing its query logic with /api/search so the two never drift apart: 

@router.get("/api/search/status")
async def search_status(ticker: str, session_factory=Depends(get_session_factory)) -> dict:
    ticker = ticker.upper()
    days, sentiment_status = await _load_search_results(ticker, session_factory)
    return {"sentiment": sentiment_status, "days": days}

Gap 2: a real fourth status grouping never needed

grouping's status is computed and returned within the same request that ran it — there's no "still working on it" state to represent, because it's always already finished by the time anything reads it. Sentiment is different: the job is fire-and-forget, so there's a genuine window where work is actually still in progress. Derived fresh from already-queried rows, checked in this priority order: 

def _compute_sentiment_status(headlines: list[Headline]) -> str:
    if not settings.openai_api_key:
        return "skipped"
    if any(h.sentiment_status == "error" for h in headlines):
        return "error"
    if any(h.sentiment_status is None for h in headlines):
        return "processing"
    return "ok"

Order matters here on purpose: an error surfaces even while other headlines are still pending, rather than being silently masked by "processing."

Gap 3: a small sample validates the pattern, not the scale

ADR 0014's own research verified 20 concurrent get_sentiment calls complete cleanly in 6.64s. That number made it into this lesson's plan unquestioned — until a real search for MSFT turned up 239 headlines in its 7-day window, an order of magnitude more. Firing all 239 through one unbounded asyncio.gather made every single one time out together, not a clean "first 100 succeed, the rest queue." httpx's default client caps at 100 connections; that much real simultaneous load against OpenAI's own rate limiting backed the pool up faster than requests could drain, pushing the queued remainder past the 10-second timeout as a group. 

semaphore = asyncio.Semaphore(20)

async def _get_one(headline: Headline):
    async with semaphore:
        ...

Re-verified against the same real batch after the fix: 238/239 succeeded on the first pass, one genuine transient failure. The page-level status correctly showed error for that one real failure — masking nothing, exactly as designed — and the retry path (a second /api/search call, the same mechanism that makes a previously-skipped headline eventually resolve once a key gets configured) picked it up: 239/239 on the next attempt.

The math, checked against real data, not just the mocked tests

One real MSFT Story — three headlines about the same dividend increase, each independently scored: 

82  bullish     "Microsoft raises its dividend 8%..."
75  reassuring  "How Microsoft's Dividend Boost Ties to AI Spending"
35  concerning  "Microsoft (MSFT) Could Be 18% Overvalued..."

(82 + 75 + 35) / 3 = 64.0 — exactly what the Story's own sentiment_average column held after the incremental-update formula ran on real, live data. The synthetic tests already proved the formula was correct in isolation; this is what proves it held up once real, independently generated scores ran through it for real.

Check your understanding

Q1. Why does /api/search/status not accept an arq_redis dependency at all?

Reveal answer

It's not just a convention -- it's a structural guarantee. Without that dependency injected, there's no object in scope this endpoint could even call enqueue_job on. It's provably incapable of triggering a job, not just written to avoid doing so.

Q2. 238 of 239 headlines succeeded, but the page still showed "error", not "processing" or "ok". Is that a bug?

Reveal answer

No -- that's the priority order working exactly as designed. "error" is checked before "processing", specifically so a real failure is never hidden just because most of the batch is still fine or still pending. One genuine error is enough to report error, on purpose.
