The actual grouping logic

Lessons 16–18 finally get used for real — and three real bugs only showed up once real data forced them, not before.

No dedicated tests in this lesson, deliberately — same shape lesson 7 had. What follows is verified live against the real running stack, not mocked. Lesson 20 adds the dedicated respx/Milvus- mocked suite.

The shape: batch the easy part, do the hard part one at a time

Every genuinely-new headline from a fetch run gets embedded in one batched request (lesson 18) — that part is embarrassingly parallel, nothing about one headline's embedding depends on another's. Matching is the opposite: it has to run sequentially, oldest-published-first, because headline N's candidate Stories include ones headline N-1 in this same loop just created. Two near-duplicate headlines arriving in the same fetch need the second one to find the first one's freshly-made Story.

backend/src/ticker_backend/providers.py

for headline, vector in zip(news_headlines, embeddings) if match_news else []:
    day = headline["published_at"].astimezone(EASTERN).date().isoformat()
    story_id = await _match_or_create_story(ticker, day, vector, session)
    await session.execute(update(Headline).where(Headline.id == headline["id"]).values(story_id=story_id))

Only genuinely-new headlines, never re-touching a known one

/api/search re-fetches from EDGAR/Finnhub on every call, including every Refresh — the existing upsert already handled that by design (dedup-by-URL). What it never did before this lesson was distinguish which headlines were actually new. Doing that turned out to need no new query at all — just reading a bit more out of the upsert Postgres was already running: 

stmt = stmt.on_conflict_do_update(...).returning(
    Headline.id, literal_column("(xmax = 0)").label("was_inserted")
)

xmax is one of Postgres' own system columns — 0 means nothing has touched this row's tuple, i.e. it was a genuine insert, not the ON CONFLICT branch. Verified directly against a real session before trusting it (not assumed from a half-remembered trick): insert a row, expect true; upsert the same row again, expect false. Both held.

Why this matters isn't just efficiency. Spec 0002 is explicit that a Story's assignment, once made, is permanent — an already-known headline's story_id must never be touched again, not just "usually isn't." This is the mechanism that guarantees it.

Bug 1: a match that should have happened, didn't

First live test: two headlines about the same fictional event, worded differently, real cosine similarity 0.92 — comfortably above any reasonable threshold. They landed in two separate Stories anyway. Milvus's own docs had already named the reason back in lesson 16: insert() doesn't make data searchable until the collection is flush()ed. The second headline's search ran before the first's insert was visible.

Bug 2 (found fixing bug 1): a good fix that didn't scale

Adding an explicit flush() after every insert fixed the correctness — the same two-headline test then grouped correctly. But flush() seals a real segment; calling it after every single new Story is expensive. A real fetch for a popular, rarely-searched ticker (MSFT, 249 headlines, almost all genuinely new) didn't finish inside 20 seconds — comfortably past job_timeout_seconds's 10s budget.

The actual fix needed research, not another guess: Milvus's search() accepts a consistency_level parameter. "Strong" gives the same read-your-own-writes guarantee — a same-process insert visible to the very next search — without sealing a segment: 

hits = await _run_milvus(
    lambda: get_milvus_client().search(
        collection_name=STORY_PRIMARIES_COLLECTION,
        data=[vector],
        filter=_milvus_ticker_day_filter(ticker, day),
        limit=1,
        consistency_level="Strong",
    )
)

Verified live, both ends: a direct insert-then-search round trip with no flush() at all found the just-inserted vector in ~5ms. The same 249-headline MSFT fetch that hadn't finished in 20+ seconds with flush() completed end to end in 3.86 seconds with consistency_level instead — same correctness, roughly 5x+ faster at real scale.

Bug 3: a key name assumed from someone else's example

Matching a hit's primary key back to a real Story crashed with KeyError: 'id'. The generic pymilvus doc example used a schema whose primary key field happened to be named "id" — this collection's primary key is named story_id (ADR 0011), and Milvus surfaces search results under whatever name the schema actually gave the field, not a fixed generic key. A direct insert-then-search round trip, printing the raw result, settled it in one command rather than a second guess: 

{'story_id': 'test-story-1', 'distance': 1.0, 'entity': {}}

Making tests safe without building lesson 20 early

Wiring grouping directly into fetch_and_persist_headlines meant every existing test that persists a real "news" headline would now try to call OpenAI and Milvus for real — not silently ( respx raises on an unmocked route rather than passing a request through), but a real regression either way. Rather than retrofit full mocking into the existing suite ahead of schedule, news- matching gates on whether OPENAI_API_KEY is actually configured: 

match_news = bool(news_headlines) and bool(settings.openai_api_key)

This isn't just a test workaround — it's the same graceful-degradation instinct this project already uses elsewhere (a down worker still shows existing data). No key configured means headlines still get fetched and deduped correctly; they're just left ungrouped until grouping infrastructure is actually available, same staged-rollout spirit as story_id's own nullable column. It also happens to be exactly why the existing 23 tests kept passing untouched: no test environment has ever had a real OPENAI_API_KEY configured.

Check your understanding

Q1. Why does matching have to run sequentially (oldest headline first), when embedding all of them can be one single batched call?

Reveal answer

Embedding one headline's text has no dependency on any other headline, so batching is free. Matching does have a dependency: a later headline in the same run might be a near-duplicate of an earlier headline in that same run, and needs to find the Story that earlier headline just created. Processing in random or parallel order could let two near-duplicates both "found" their own separate Story instead of the second one joining the first's.

Q2. The fix for bug 1 (explicit flush()) was correct but got replaced. What was actually wrong with it, given it did fix the bug?

Reveal answer

Nothing was wrong with its correctness -- it genuinely fixed the missed-match bug. The problem was cost: flush() seals a real segment, and calling it after every single new Story is expensive at real volume (a 249-headline fetch took over 20 seconds). consistency_level="Strong" on the search call gives the identical read-your-own-writes guarantee without that per-insert cost -- same correctness, dramatically cheaper.

Q3. Why does news-matching check settings.openai_api_key before running, rather than always attempting it and catching the failure?

Reveal answer

An unconfigured key is an expected, permanent state in some environments (every local test run, CI) -- not a transient failure worth retrying or logging as an error. Checking first lets filings still group correctly and headlines still persist correctly regardless, exactly the same graceful-degradation shape this project already uses for a down worker, rather than treating "grouping infrastructure isn't configured" as an exceptional case.
