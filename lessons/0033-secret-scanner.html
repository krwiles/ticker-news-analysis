A secret scanner in pre-commit and CI

What actually got configured to catch a leaked API key before it reaches this public repo — and a live test that caught a gap in how the tool itself works, before trusting it.

Not a bug, not a feature — a guardrail. The repo is public, nothing has leaked so far, but that's discipline, not a mechanism. And more sensitive values are coming (an OAuth client secret, a session-signing key) than the two API keys sitting in .env today.

Choosing a tool: shape-matching, not live-checking

Two real candidates exist: Gitleaks and TruffleHog. They ask genuinely different questions. Gitleaks asks "does this string match the shape of a known secret?" — regex against known providers' formats, fully offline. TruffleHog asks "is this credential actually live right now?" — it makes a real network call per candidate to verify. That's more precise, but it costs a network round-trip on every scan and is built for repos noisy enough that cutting triage volume matters. This project has two keys today. Gitleaks — fast, offline, a maintained GitHub Action with SARIF output — fits a personal-project scale; TruffleHog's extra depth isn't needed yet.

Prove the baseline before turning on a blocking gate

A guardrail that might reject your own history on day one, unverified, is a bad way to introduce one. Before wiring anything blocking, a real scan ran against every commit: 

gitleaks detect --source . --log-opts="--all"
# 87 commits scanned, 0 leaks found

Clean — including against .env.example's placeholder values and the test suite's "test-key-not-real" strings scattered through dozens of monkeypatch calls, none of which happened to trip a false positive. That meant no allowlist file (.gitleaks.toml) was needed yet — same instinct as skipping a linter in lesson 15 until a real reason to configure one shows up.

What actually got configured

Two small additions, both extending plumbing that already existed.

.githooks/pre-commit

python3 "$(git rev-parse --show-toplevel)/scripts/check_comment_length.py" || exit 1

# Blocks a commit whose staged changes look like a real API key/token/credential.
gitleaks protect --staged --no-banner

protect --staged scans only what's about to be committed — fast, same scope as the comment-length check next to it. The || exit 1 on the first line is a small but real fix made along the way: with a second command now following it, a failing comment check needed to be propagated explicitly, or a passing gitleaks call could mask it.

.github/workflows/ci.yml

secret-scan:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0   # full history, not just this push's commits
    - uses: gitleaks/gitleaks-action@v2

This is the backstop: the local hook only runs on a machine that ran git config core.hooksPath .githooks. CI scans every push and PR regardless.

A live test that found a real gap — in the tool, not the code

Verifying the hook actually blocks something started with a synthetic OpenAI-shaped key: sk-proj-aBcDeFgHiJkLmNoPqRsTuVwXyZ0123456789.... Gitleaks let it straight through. That looked like a broken setup — it wasn't. Gitleaks' openai-api-key rule requires the real format's embedded marker: a base64-encoded T3BlbkFJ (which decodes to the literal text "OpenAI") baked into every real key OpenAI issues. A merely sk--prefixed random string doesn't have it — so the tool was correctly declining to flag something that wasn't actually shaped like a real key.

Re-tested with a Finnhub-shaped fake instead — this project's other real key: 

echo 'FINNHUB_API_KEY=<20-char-alphanumeric-token>' > fake-secret-test.txt
git add fake-secret-test.txt && git commit -m "test"
# RuleID: finnhub-access-token — leaks found: 1 — commit blocked, exit 1

(The real token used to verify this was a genuine-shaped 20-character alphanumeric string — redacted here on purpose, since a working example would trip this very rule on this file too.)

Caught immediately, by a rule gitleaks ships specifically for Finnhub tokens. The real takeaway: "shape-matching" isn't a vague heuristic — it's dozens of specific, maintained per-provider patterns, and testing with an incorrectly-shaped fake proves nothing except that the fake was wrong.

A mistake made and fixed, mid-lesson

That first verification commit landed directly on main — a real process slip, not a tool one. The fix was git revert, not git reset --hard: revert adds a new commit that undoes the change, leaving history intact and honest about what happened; a hard reset would have erased the mistake from the record entirely, and was refused for exactly that reason. Two small no-op commits (the mistake and its revert) are still visible in this project's history as a result — a deliberate trade against pretending it never happened.

Watched running for real, not just trusted from the YAML

Pushed as a PR and watched on GitHub's own runners, same discipline lesson 15 used for its own first CI jobs: all four jobs green on the first real run, secret-scan included.

Check your understanding

Q1. Why does TruffleHog's live-credential-verification make it a worse fit than Gitleaks for a fast, blocking pre-commit hook?

Reveal answer

Verifying a credential is live means making a real network call per candidate secret found. A pre-commit hook needs to be near-instant so it doesn't get in the way of every commit; a network round trip (or several) on each one works against that. Gitleaks' regex-based shape-matching is fully offline and runs in well under a second.

Q2. The baseline scan came back clean. Why run it at all before turning on a blocking gate, instead of just trusting the earlier informal check of the two known keys?

Reveal answer

The earlier check only looked at two specific values by eye. A real gitleaks scan covers every commit and every kind of secret its rules know about, and it also doubles as the false-positive check — confirming things like .env.example's placeholders and the test suite's fake key strings don't trip the tool before it starts blocking real commits.

Q3. A synthetic OpenAI-shaped key wasn't flagged. Was that a bug in gitleaks?

Reveal answer

No — it was correct behavior. Gitleaks' openai-api-key rule specifically requires the real format's embedded T3BlbkFJ marker (base64 for "OpenAI"). A random sk--prefixed string without that marker genuinely isn't shaped like a real OpenAI key, so declining to flag it is the rule working as designed, not a miss.

Q4. Why revert instead of a hard reset to fix the accidental commit to main?

Reveal answer

A hard reset rewrites history so the mistake never appears to have happened — irreversible once done, and it erases the record along with the error. A revert adds a new commit undoing the change on top of history, which is itself reversible (you can revert the revert) and keeps an honest trail of what actually happened, at the cost of two extra no-op commits.
