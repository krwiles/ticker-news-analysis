Filing content extraction

A three-tier plan, shrunk to two before any code was written — and the same specificity bug found twice, once in planning and once for real, on the exact next piece of logic it hadn't been fixed for yet.

The plan going into this lesson had a "tier 1": follow a filing's table-of-contents anchors straight to its real MD&A section. It never got built. Here's the real evidence that killed it, and what replaced it instead.

Tier 1's death: one heuristic that worked on the case that found it, and broke the case it was meant to fix alongside

Earlier research (ADR 0014) found Apple's and Microsoft's table-of-contents links both use real anchor ids — but structured differently. Apple's ids are opaque (i719388195b384d85a4e238ad88eba90a_94); Microsoft's are human-readable (item_7_managements_discussion_analysis_f). The fix that made Microsoft work — "match on the anchor id, not the visible label" — was never rechecked against Apple, the filer it was originally verified against. An id-only strategy would have broken Apple silently the moment it fixed Microsoft.

Combining both heuristics and testing against five more real filers — spanning micro-cap to mega-cap — found something worse than a matching gap: 

Richardson Electronics  -> matched (id-substring)
Applied Industrial Tech -> matched (label-text)
Western Digital         -> NO MATCH -- link and label aren't co-located in the markup at all
George Risk Industries  -> NO MATCH
Standex International   -> NO MATCH

Western Digital's table of contents links wrap only the page number ("4", "10", "24") — the actual "Item 7." text sits in a separate table cell. That's not a matching-heuristic problem a smarter regex can fix; it needs a real DOM parser walking table structure, which is a genuine new dependency, not a tweak. **2 real successes out of 5.** Not reliable enough to build on. Tier 1 was dropped before a single line of it was ever written.

What replaced it: no anchors at all, just text — validated across twelve real filers

A pure text search for the heading itself, once made specific enough, worked far better than any anchor-chasing did: 

_ITEM_7_HEADING_RE = re.compile(r"Item\s*7\.?\s*(?:Management|MANAGEMENT)", re.IGNORECASE)
_NEXT_ITEM_HEADING_RE = re.compile(
    r"Item\s*7A\.?\s*(?:Quantitative|QUANTITATIVE)|Item\s*8\.?\s*(?:Financial|FINANCIAL)",
    re.IGNORECASE,
)

Two things had to be true for this to actually work: take the last match of the heading (the first is always the table of contents' own listing, not the real section), and require the real title text to follow the item number — a bare number alone isn't specific enough, confirmed live when it matched a stray citation and produced 24 tokens of garbage for two different filers before this fix.

The exact same bug, found a second time — this time in the code, not the plan

Live verification against Apple returned 236 characters instead of the ~18,000 already measured during planning. The cause: Apple's own real MD&A opening sentence contains an inline cross-reference — "...accompanying notes included in Part II, Item 8 of this Form 10-K..." — and the original next-heading pattern (a bare Item 8) matched that sentence as if it were the real section boundary, cutting the extraction off after one line.

This is the identical specificity mistake the Item 7 heading pattern was already fixed for, just one step further down the pipeline, not yet carried over. Fixed the same way: require the real, SEC-standardized titles ("Quantitative", "Financial") to follow the item number, not just the bare number. A synthetic test fixture, built from realistic-but-simplified text, never would have caught this — only a real document happened to contain the exact kind of inline reference that broke it.

The fallback that covers everything else, with no special-casing per filing type

If the heading isn't found at all — true for every 8-K, S-1, and DEF 14A, none of which use "Item 7" numbering — or if it's found but the section starts with "incorporated ... by reference" (a real case: Friedman Industries' actual MD&A lives in a separate exhibit, not in this document), the whole document gets truncated from its own start instead. Validated in both directions across the full 12-filer sample: the reference-check fires on the one filer that needs it, and stays silent on the other 11, whose real MD&A content sits directly in the document.

Check your understanding

Q1. Why does the heading search take the last match of "Item 7", not the first?

Reveal answer

The first mention is always the table of contents' own listing, not the real section. Taking the last match is what actually lands on the real heading -- the same "don't trust the first occurrence" instinct that also motivated requiring the real title text to follow, since a bare number match could hit a stray citation anywhere in the document.

Q2. The 236-character bug and the original "bare Item 7" bug -- are these the same bug, or two different ones?

Reveal answer

Same underlying mistake, found twice: a bare item-number match isn't specific enough to distinguish a real section heading from an unrelated mention of that number elsewhere in the document. The first instance was caught during planning (Item 7's own heading); the second was the identical mistake in the *next*-heading pattern (Item 7A/8), not yet fixed because it hadn't been built yet -- found only once the real implementation was tested against a real document.
