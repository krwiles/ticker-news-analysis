Lesson 39 · ticker-news-analysis stack (Roadmap Phase 2 — secrets management)

Building secrets management in this repo

ADR 0017 decided what to build; this lesson is the build — and three things found only by checking the running stack, one of which was the real key printed in the logs.

Lesson 38 gave the ladder: env vars → per-service files → a secrets manager → dynamic credentials. This repo just moved from rung 1 to rung 2, on purpose, in a shape that lets Phase 4's Vault swap only where the files come from. One constraint held throughout: the single image and three APP_MODEs of ADR 0001 did not change.

Where we started

One YAML anchor, &app-env, was merged into all three services. Every key therefore landed as a plain environment variable in every container. Who actually used what (from grepping the code):

ServiceNeedsWas handed
workerFinnhub key, OpenAI key, Postgres passwordEverything
apiPostgres password, and one fact: is OpenAI configured?Everything, including both provider keys
uiNothing — it serves static filesEverything

That's lesson 38's "over-broad blast radius" in one table: the container that serves files to the internet held the paid OpenAI key it never uses.

Move 1: give each service only what it uses

docker-compose.yml

secrets:                       # declared once, top level
  finnhub_api_key:
    file: ./secrets/finnhub_api_key
  # …openai_api_key, postgres_password likewise

  worker:
    secrets: [postgres_password, finnhub_api_key, openai_api_key]
  api:
    secrets: [postgres_password]
  ui:
    environment: { APP_MODE: ui }   # no secrets, no data-store config at all

Docker's docs state that services can only access a secret when explicitly granted it — the deny-by-default behavior that makes this least privilege rather than just tidiness. Same image, three different grants: ui's /run/secrets is empty.

api still needed one fact from the OpenAI key: _compute_sentiment_status in search.py reports skipped when sentiment isn't configured. It now reads a non-secret boolean, settings.sentiment_configured, instead of the key. The original plan derived that boolean with Compose's ${OPENAI_API_KEY:+true} — which stopped working the moment the key left .env, because Compose then had nothing to interpolate. The fix: init-secrets.sh writes an explicit SENTIMENT_CONFIGURED=true|false flag. Lesson: a design that was correct on paper can depend on the very thing you're removing.

Move 2: files, read by the settings class

Compose mounts each secret at /run/secrets/<name>. pydantic-settings maps a file's name to a field name and its contents to the value:

backend/src/ticker_backend/config.py

model_config = SettingsConfigDict(
    env_file=".env",
    secrets_dir=SECRETS_DIR if Path(SECRETS_DIR).is_dir() else None,
    extra="ignore",
)
finnhub_api_key: str = ""     # ← read from /run/secrets/finnhub_api_key

Precedence trap. pydantic-settings' documented order is init args → environment variables → dotenv → secrets files → defaults. A stale FINNHUB_API_KEY left in .env would silently beat the mounted file. There's a test that pins exactly this behavior (test_an_env_var_silently_outranks_the_secrets_file), and it's why init-secrets.sh --from-env strips the keys out of .env rather than copying them.

The database URL is now assembled, not stored. With the password in a file, a single DATABASE_URL string can't hold it. Settings.database_url builds a SQLAlchemy URL object from parts, and a test proves a password like p@ss:/w#rd survives — hand-built URL strings break on those characters, which is a real-world bug class, not a hypothetical.

Move 3: fail fast, at the right place

REQUIRED_SECRETS_BY_MODE = {
    "ui": [],
    "api": ["postgres_password"],
    "worker": ["postgres_password", "finnhub_api_key"],   # OpenAI: deliberately absent
}

require_secrets() raises with the missing secret's name and the fix (scripts/init-secrets.sh) — never a value. It runs from create_app() and ARQ's on_startup hook, not inside Settings: settings = Settings() executes at import time, and the whole test suite imports it with no secrets present. Where a check runs matters as much as what it checks. OpenAI stays optional because spec 0005 designed sentiment to degrade gracefully.

A detail found only by running it: ARQ connects to Redis before on_startup, so a secretless worker only shows the friendly error when Redis is reachable.

Move 4: shrink the network exposure

Every data-store port (Postgres, Redis, MinIO, Milvus) was published on all host interfaces. They now bind to 127.0.0.1: your tools still reach them, your Wi-Fi neighbors can't. This matters more than it looks — Redis holds live session IDs (ADR 0016) and has no password.

The find: the real key was in the logs

While writing this lesson, reading providers.py showed the Finnhub call: 

params = {"symbol": ticker, "from": …, "to": …, "token": settings.finnhub_api_key}

The key was a URL query parameter. httpx logs every request's full URL at INFO. So docker compose logs worker printed the live key on every fetch — all the file-mounting work above did nothing about it, because it was the use of the key that leaked it. This is lesson 38's "printed in logs" leak path, sitting inside our own code.

The fix, test-first: send it in an X-Finnhub-Token header (checked against the live API — correct key 200, wrong key 401, so the header is genuinely the credential), and raise httpx's logger to WARNING as a second layer. And a lesson inside the lesson: the first version of the logging test passed even with the fix removed, because pytest leaves the root logger at WARNING. Only a deliberate-break check — remove the fix, expect red — caught a test that proved nothing.

Bootstrapping without ever printing a secret

scripts/init-secrets.sh creates ./secrets/ (mode 700, files mode 600), takes values through hidden prompts, never overwrites an existing secret, and --from-env migrates the keys out of an older .env. It is tested by running the real script against a temp directory and asserting the output contains none of the values. --rotate NAME replaces one secret; the README runbook covers recreating the container and the Postgres gotcha below.

Prove it yourself

# What can each container see? (ui: nothing; api: 1 file; worker: 3)
docker compose exec ui     ls /run/secrets
docker compose exec api    ls /run/secrets
docker compose exec worker ls /run/secrets

# No key-shaped variable in any environment
docker compose exec worker sh -c 'env | grep -iE "key|password"'

# The key must not appear in logs (prints a count; expect 0)
docker compose logs worker | grep -c "$(cat secrets/finnhub_api_key)"

# Fail-fast: same image, no secrets → named error, not a mystery auth failure
docker run --rm -e APP_MODE=api "$(docker compose images worker -q | head -1)" \
  python -c "import ticker_backend.main"

Three honest gaps, and where they go

  • An existing Postgres volume never re-reads its password file. The image reads POSTGRES_PASSWORD_FILE only when initializing a fresh data directory — our running database never exercised it, so it was proven on a throwaway container. Rotating means an ALTER USER too.
  • MinIO/Milvus still share minioadmin; Redis has no password. Loopback binding removes the exposure for now; ADR 0017 records both as required before a real deployment.
  • Files are plaintext at rest, with no audit trail and no automatic rotation. That is exactly what rungs 3–4 (Vault, Phase 4) add — and because the app reads a path, that upgrade changes the file's source, not the code that reads it.
