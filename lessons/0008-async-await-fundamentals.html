Async/await, Python and TypeScript side by side

You've been writing this since lesson 2. Here's why it's shaped the way it is — and the one place Python and JS quietly disagree.

Inserted out of order on purpose: this underpins main.py, health.py, providers.py's asyncio.gather, and the frontend's own fetch calls — all already written before this lesson existed. Better late than never; nothing here changes what you've already built, it explains why it works.

Calling an async function does not run it — in Python

This is the single biggest gotcha for anyone coming from JavaScript, and it's worth being precise: 

# Python
async def check_db() -> dict:
    print("running!")
    ...

coro = check_db()   # nothing printed yet — this is just a coroutine object
await coro          # NOW it actually runs
// TypeScript
async function checkDb(): Promise<object> {
    console.log("running!");
    ...
}

const p = checkDb(); // "running!" already printed — JS starts executing
                      // synchronously up to the first await, THEN returns
                      // a pending Promise
await p;

Same keywords, genuinely different semantics. A Python coroutine is inert until something drives it — await, or scheduling it on the event loop. A JS async function starts running immediately, like any other function call, and only pauses at its first await. Reading Python code with JS intuition here will give you the wrong mental model of execution order.

The event loop: one thread, cooperative switching

Both languages are single-threaded for this — asyncio doesn't give you real parallelism, and neither does JS's event loop. What actually happens: the loop runs one piece of code until it hits an await, then switches to whatever else is ready, and comes back later when the awaited thing resolves. It's cooperative multitasking on one thread, not threads or CPU cores doing work simultaneously.

One real difference: JS's event loop is baked into the runtime and is just always running — you never "start" it. Python's is a real object you (usually) start explicitly, though FastAPI/Uvicorn and ARQ both do this for you — you've never had to call asyncio.run() yourself in this project.

This is why main.py and worker.py never mention an event loop directly — the frameworks own that part.

Where this actually helps: I/O-bound, not CPU-bound

You've already built the textbook example. Lesson 7's providers.py: 

edgar_result, finnhub_result = await asyncio.gather(
    fetch_edgar_filings(client, company.cik, ticker),
    fetch_finnhub_news(client, ticker),
    return_exceptions=True,
)

Both calls spend almost all their time waiting on a network response — the CPU is idle, not busy. That's exactly when async pays off: while one request waits, the loop runs the other. The direct TypeScript equivalent is Promise.all: 

const [edgarResult, finnhubResult] = await Promise.all([
    fetchEdgarFilings(client, company.cik, ticker),
    fetchFinnhubNews(client, ticker),
]);

Async does nothing for CPU-bound work, in either language. If a function is actually crunching — a tight loop, image processing, heavy computation — there's no "waiting" for the loop to fill with other work. The single thread is just busy the whole time, `await` or not. Python's answer for that is multiprocessing (separate processes, side-stepping the GIL below); Node's is worker_threads (separate isolated contexts). Neither is asyncio/plain async/await.

Why await is contagious

Once one function needs to await something, its caller generally has to be async too, all the way up. It's why main.py's path operations, health.py's three checks, and now every function in providers.py are all async def — the chain starts at one real I/O wait (a DB query, an HTTP call) and propagates upward through every caller. Same in TypeScript: fetchHealth in health.ts is async specifically because it awaits fetch(...), and StatusPage.tsx's poll function is async because it awaits fetchHealth().

The one real divergence: why does Python even have this?

JS has always been single-threaded in its core execution model — async/await is just cleaner syntax over what Promise/.then() already did, with no alternative story for concurrency needed. Python is different: Python does have real OS threads (threading), but the GIL (Global Interpreter Lock) means only one thread ever executes Python bytecode at a time regardless of how many threads you spawn — so threads don't actually help with CPU-bound work, and they're relatively heavyweight for I/O-bound work too. asyncio exists as a cheaper way to handle many concurrent I/O waits on one thread, without needing OS threads at all. JS never needed that argument — it just never had real shared-memory threads in the first place.

When not to reach for async — a checklist

  • Is this waiting on something external (network, disk, a database)? → async genuinely helps.
  • Is this crunching numbers or looping over large data in memory? → async does nothing; the thread is busy, not idle. Reach for multiprocessing (Python) or worker threads (Node) instead.
  • Is this a one-off script with no concurrent work happening? → plain synchronous code is simpler and loses nothing — async has a real readability/complexity cost when there's nothing to overlap.

Check your understanding

Q1. In Python, result = fetch_finnhub_news(client, ticker) (no await) — has the HTTP request been sent yet?

Reveal answer

No. result is just a coroutine object; none of the function's code has run. The equivalent line in TypeScript would have already started executing up to its first await — this is the core Python/JS divergence from this lesson.

Q2. Would rewriting fetch_edgar_filings to do heavy in-memory JSON parsing of a huge response with async/await make that parsing step faster?

Reveal answer

No. Parsing is CPU-bound — the thread is busy computing, not waiting on anything. Async only overlaps waiting time; it can't parallelize work that's actually using the CPU the whole time.
