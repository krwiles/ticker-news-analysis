Secrets management at a high level: how production systems keep keys safe

Not Docker-specific and not this repo's specifics (that is lesson 39) — the threat model and the storage ladder every production system climbs, so you can place any setup on it.

The tell that you have a secrets management problem, not just a secrets problem: the question stops being "where do I put this key?" and becomes "who can read it, how would I know if they did, and how fast can I replace it?"

Secret vs. config: one test

The twelve-factor app's Config factor gives a clean litmus test: could you open-source the codebase right now without leaking a credential? Anything that fails the test has to live outside the code. In this repo the Finnhub key, OpenAI key, and Postgres password fail it. The SEC user-agent string and Google client ID do not — they're config, not secrets, and treating them as secrets only makes them harder to work with.

A subtlety worth holding onto: twelve-factor says put config in environment variables. Later guidance from Docker, OWASP, and Kubernetes says put secrets somewhere stricter. There's no contradiction — env vars were a big step up from hardcoding, and the industry has since learned that secrets deserve more than that step.

How secrets actually leak

Almost every real incident is one of these. Notice how few involve a clever attacker.

  • Committed to git. History is forever; deleting the file later doesn't remove the secret from old commits, and automated scanners watch public repos for exactly this.
  • Baked into an image or build log. A COPY .env or a CI step that echoes a variable puts the secret where anyone who can pull the image or read the log can see it.
  • Sprayed into every process's environment. Docker's docs note environment variables are often available to all processes and can be printed into logs while debugging without you noticing. On Linux, any process with the right privileges can also read another's variables from /proc/<pid>/environ.
  • Over-broad blast radius. One compromised low-value container hands over every key the whole system holds, because they were all shared.
  • Long-lived and never rotated. A key that's valid for years is valid for whoever copied it years ago — an ex-teammate's laptop, an old backup.
  • Abused through the app, not stolen. An anonymous endpoint that triggers paid API calls lets strangers spend your key without ever seeing it. The fix there is rate limits and spend caps, not storage.

The lifecycle, not a one-time setup

OWASP's Secrets Management Cheat Sheet frames every secret as moving through four stages: creation (strong, minimally-permissioned), rotation (replace regularly, so a stolen credential works only briefly), revocation (disable the instant it's compromised), and expiration (a built-in end date). Most homemade setups only ever do the first stage. The rest is what a "management" system adds.

The storage ladder

Each rung fixes something the one below it can't:

RungWhat it fixesWhat it still can't
0. Hardcoded in sourceNothing.Leaks with the code, forever.
1. Environment variablesKeeps secrets out of git; changes per deploy.Visible to every process, logs, inspect; one shared blast radius.
2. Files mounted per serviceOnly granted services see it; filesystem permissions apply; not in env dumps.Still plaintext at rest; rotation and auditing are manual.
3. A secrets manager (Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager)Encrypted at rest, identity-based access, audit log of every read, central rotation.The secret is still static and long-lived unless you go one rung further.
4. Dynamic, short-lived credentialsVault mints a unique database user per request with a lease; expiry revokes it. A leak is small and self-healing, and every credential traces to one service instance.Needs real infrastructure and an app that fetches credentials at runtime.

Rungs 2 and 3 share a delivery shape: the app reads a file at a path. A Vault Agent, a Kubernetes secret volume, and a cloud secret-store driver all write a file; the app doesn't care which wrote it. That's why choosing rung 2 today doesn't paint you into a corner — moving up changes the source of the file, not the app.

Five principles that hold at every rung

  1. Least privilege. Each service gets only the secrets it uses. "Engineers should not have access to all secrets" applies equally to containers.
  2. Centralize. Few places to look, one lifecycle to follow — even if more than one tool coexists.
  3. Inject at deploy time. Never in the image, never in the repo, never echoed by CI. A public deployment's secrets live in the platform's secret store, not a .env copied onto a server.
  4. Detect leaks early. Secret scanners in a pre-commit hook and in CI (this repo runs gitleaks in both) catch the commonest failure before it ships.
  5. Fail loudly. A service that starts without a required secret should stop with a clear message rather than limp along and fail later with a confusing authentication error.

Kubernetes trap: "Secret" does not mean "encrypted"

Kubernetes Secrets are, by default, stored unencrypted in etcd — the base64 you see is encoding, not protection, and anyone with API access can read them. Its docs recommend encryption at rest, least-privilege RBAC, and external secret stores. Worth knowing now because Phase 4 of this roadmap is Kubernetes, and "we used Kubernetes Secrets" is a weaker claim than it sounds.

When it leaks anyway: the response order

OWASP's incident sequence, and the order matters:

  1. Revoke at the provider first — stopping the bleeding beats everything else.
  2. Rotate — issue and deploy a replacement.
  3. Clean up the leak's source (logs, repos, history — carefully).
  4. Investigate access logs to learn what the secret was used for. This is only possible if you had auditing to begin with, which is the strongest argument for rung 3.
