OpenAI sentiment classification call

Same shape lesson 18 used for embeddings — prove the call works in isolation, nothing wired yet — except the model itself talked back with a real problem this time, not just a shape to confirm.

No filing content, no job wiring, no Story aggregate — that's lessons 25/26. This lesson is one new function, get_sentiment(), and the two things it took to make it trustworthy: a schema that guarantees the shape, and a prompt fix for a failure mode the model produced on the very first real call.

Not a batch call — a real difference from embeddings, not just a smaller one

get_embeddings() sends many headlines in one request, using OpenAI's native array input support. Chat Completions has no equivalent — every call is one conversation, one response, always. So get_sentiment() takes a single piece of text and returns a single result: 

async def get_sentiment(text: str, client: httpx.AsyncClient) -> dict:
    ...
    response = await client.post(
        "https://api.openai.com/v1/chat/completions",
        headers={"Authorization": f"Bearer {settings.openai_api_key}"},
        json={
            "model": OPENAI_SENTIMENT_MODEL,
            "messages": [...],
            "response_format": {"type": "json_schema", "json_schema": {...}},
        },
    )

Concurrency across many headlines happens the other way — firing several get_sentiment() calls at once with asyncio.gather, the same pattern already verified live elsewhere in this project (20 concurrent calls, 6.64s wall-clock). That's lesson 26's job to build, not this one's — mirroring this function's shape after get_embeddings' batching would have been the wrong move here, not just an unnecessary one.

Structured Outputs: guarantee the shape, don't parse free text

response_format: {"type": "json_schema", "json_schema": {...}, "strict": true} tells the model to return exactly {"score": int, "gloss": str, "rationale": str}, not a paragraph that happens to contain those facts somewhere. Verified live against the real API before trusting it — OpenAI's own docs were ambiguous about which current models support this on which endpoint, so rather than trust an uncertain summary, the real thing got tested directly against gpt-5-nano on /v1/chat/completions. It worked, cleanly, on the first try.

The first real call also proved something was wrong

Spec 0005's own Success Criteria are explicit: the one-word gloss must never just restate the enum (gloss = "positive" fails outright). The very first live call, with a prompt that only asked for a score/gloss/rationale with no further guidance, produced exactly that failure: 

{"score": 92, "gloss": "Positive", "rationale": "Apple beat earnings estimates..."}

Not a hypothetical risk the spec worried about in the abstract — the very first real output. Fixed with an explicit instruction in the system prompt (never restate positive/neutral/negative; give a more specific word — bullish, reassuring, routine, concerning, alarming) and reverified across three different real-ish cases before writing the real function: 

Apple beats earnings expectations...       -> score: 97, gloss: "bullish"
Company X reports layoffs...                -> score: 28, gloss: "concerning"
Company Y schedules annual shareholder mtg. -> score: 50, gloss: "routine"

Three genuinely different situations, three genuinely different glosses — not the same three words recycled, and never the bare enum.

A second real bug, found while trying to verify the first fix

A standalone script importing get_sentiment directly failed immediately, before ever reaching OpenAI — the exact same NoSuchModuleError bug found and fixed in health.py during an earlier lesson. providers.py had the identical root cause: pymilvus's own import unconditionally loads this repo's root .env (meant for dbmate), which can silently corrupt DATABASE_URL if it happens before ticker_backend.config is imported. Every existing test file that touches providers.py happened to dodge this by importing config first anyway — never by design, just coincidence of import order. Fixed the same way: reordered the import, with a comment explaining why the order actually matters, so a future edit doesn't undo the fix without realizing it.

Check your understanding

Q1. Why can't get_sentiment batch many headlines into one request the way get_embeddings does?

Reveal answer

The embeddings endpoint has native array-input support -- one request, many texts in, many vectors out. Chat Completions doesn't work that way: every call is exactly one conversation, one response. Concurrency across many headlines has to happen by firing multiple separate calls at once (asyncio.gather), not by combining them into one request.

Q2. The very first live call returned gloss: "Positive". Was that a bug in get_sentiment's code?

Reveal answer

No -- the code worked exactly as written; the schema was satisfied, the call succeeded. The problem was the prompt itself gave the model no reason not to just restate the enum. Fixed by instructing the model explicitly never to do that, then reverifying live across several different real cases -- a prompt problem, not a code problem, but a real one either way.
