Lesson 14 of 14 · ticker-news-analysis stack (feature arc — capstone)

Today/Recent, category badges, and the Refresh button

The arc-2 capstone: spec 0001 goes from modeled to actually built.

Before this lesson, three real gaps remained against docs/specs/0001-first-feature.md: SearchPage.tsx merged today/recent into one list, category showed as plain text, and there was no Refresh button at all. All three close here — see docs/plans/0014-*.md's completeness checklist for the full spec-by-spec accounting.

Stopping the merge — the backend's guarantee was there all along

split_today_recent (lesson 9) has guaranteed, since before the frontend even existed, that a headline lands in exactly one of today or recent — DST-tested carefully in lesson 10. The frontend's own [...results.today, ...results.recent] line was quietly throwing that guarantee away, presenting it back to the user as one undifferentiated list. Removing that line and rendering two real, headed sections doesn't add a new guarantee — it just stops hiding the one that already existed: 

<section>
  <h2>Today</h2>
  <HeadlineList headlines={results.today} emptyMessage="No headlines today." />
</section>
<section>
  <h2>Recent</h2>
  <HeadlineList headlines={results.recent} emptyMessage="No other headlines in the past week." />
</section>

The one guarantee that genuinely needed a new test, not just a rendering change: spec 0001 says an empty Today list is "normal, not a bug" — even when Recent has real entries right next to it. That's not automatically true just because two sections exist; it needed its own test constructing exactly that shape (empty today, populated recent) and asserting Today reads as a plain, calm empty message, not broken or missing.

CategoryBadge and SearchStatus: the same shape as StatusTile, on purpose

Both new components are the same pattern: a small enum mapped to a color and a label. Neither is reused anywhere else yet — same as StatusTile.tsx wasn't, when it was first extracted from StatusPage. The reason to still give each its own file isn't reuse, it's testability: a mapping table is exactly the kind of thing worth verifying in isolation (does "filing" really produce "Filing" in purple? does "success" really produce a different message than "partial_failure"?) rather than asserting on it buried inside a much bigger page render.

One deliberate content decision worth naming: SearchStatus shows a message for success too — "All sources responded." — not just the two failure states. Spec 0001 asks to "surface a simple success/partial-failure/complete-failure status," all three; knowing the latest news genuinely got fetched is real information, not just noise to suppress until something goes wrong.

Refresh: the payoff of lesson 13's whole design

This is the smallest addition, because lesson 13 built the hook point for exactly this on purpose: 

function handleRefresh() {
  if (urlTicker) {
    runSearch(urlTicker);
  }
}

Worth being precise about why this can't just be "let the user resubmit the search bar again": submitting an unchanged ticker calls setSearchParams with a value the URL already has, so the URL doesn't actually change, so the useEffect that watches it never re-fires. Refresh has to call runSearch directly, sidestepping the URL entirely — spec 0001's own words, "the Refresh button just calls the exact same GET /api/search again for the currently-shown ticker," turn out to describe a real mechanical necessity, not just a simplicity choice.

A non-goal satisfied for free

Spec 0001's Non-goals rule out "stale-then-fresh loading" for v1 — showing old results while a new fetch runs quietly behind them, then swapping. {results && !loading && (...)} already hides the whole results block whenever loading is true, and that line hasn't changed since lesson 11. Refresh reuses the exact same loading state as every other search, so pressing it correctly hides the old results and shows "Searching…" — not because this lesson added that behavior, but because it was already there, built for the very first search, and Refresh never needed anything different.

Check your understanding

Q1. Why does the "empty Today, populated Recent" test matter, when the two-section split itself already looks correct just from reading the JSX?

Reveal answer

Reading the JSX shows that two sections exist and each has an emptyMessage prop -- it doesn't prove that an empty Today section actually renders calmly next to a populated Recent one, rather than looking broken, cut off, or like a loading state that got stuck. Spec 0001 explicitly calls this case out as something that must read as normal -- that's a behavioral claim, and only a test that constructs exactly that shape (not just "both empty" or "both populated") can verify it.

Q2. Why can't Refresh just call the search bar's own submit handler with the current ticker already in the box?

Reveal answer

The search bar's submit handler calls setSearchParams, which only triggers a new fetch by changing the URL and letting the effect react to that change. Submitting the same ticker that's already in the URL doesn't change anything the effect is watching, so no new fetch would fire. Refresh has to call runSearch directly, which is exactly why it's a separate function rather than a wrapper around the existing submit path.
