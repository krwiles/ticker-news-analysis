Frontend: per-day lists + the Story component

Consuming lesson 21's new shape, a native disclosure instead of any local state, and a date-formatting bug caught before it ever shipped.

Capstone of this arc, same role lesson 14 played for arc 2: spec 0002 is fully built after this, not just modeled. Pure frontend — no backend or API changes, everything consumed here already shipped in lesson 21.

One headline's markup, extracted once, used twice

A Story's primary and its other members need to render identically — same title/link, same category badge, same outlet/date line, same optional summary. Rather than write that markup twice (or have it quietly drift apart over time), it's pulled into one component and shared: 

export function HeadlineCard({ headline }: HeadlineCardProps) {
  return (
    <div className="rounded-lg border border-slate-200 bg-white px-4 py-3 shadow-sm">
      ...
    </div>
  );
}

Story then becomes almost embarrassingly small: <HeadlineCard headline={story.primary} />, plus — only when there's anything to show — a disclosure for the rest.

An expandable list with zero local state

The obvious React instinct is a boolean useState and an onClick toggling it. None of that is needed here — HTML already has a native disclosure element that does exactly this: 

{story.other_members.length > 0 && (
  <details>
    <summary>+{story.other_members.length} more source{story.other_members.length === 1 ? "" : "s"}</summary>
    <div>
      {story.other_members.map((member) => <HeadlineCard key={member.url} headline={member} />)}
    </div>
  </details>
)}

The browser handles open/closed entirely on its own. A Story of one (the common case for most headlines) renders no disclosure at all — the condition on other_members.length means there's nothing to click, not a disclosure that opens onto emptiness.

A real bug, caught before it shipped: date parsing that silently shifts a day

day.date arrives as a plain string, "2026-09-16" — no time, no timezone. The obvious way to turn that into a human-readable label is new Date(day.date). That's exactly the wrong move: 

new Date("2026-09-16")              // parsed as UTC midnight
  .toLocaleDateString()             // formatted in the *viewer's local* timezone

For anyone west of UTC — including US Eastern, the timezone this date came from in the first place — that can render as September 15, silently. Same class of bug the backend's DST tests exist to catch, just surfacing on the frontend side now that dates cross the wire as bare strings. Fixed by parsing the components manually and using the local-time constructor, which never gets reinterpreted through another timezone: 

function parseIsoDateLocal(isoDate: string): Date {
  const [year, month, day] = isoDate.split("-").map(Number);
  return new Date(year, month - 1, day);
}

Caught with a dedicated regression test before this ever reached a browser — not found by clicking around and noticing the date looked wrong.

HeadlineList — the component that rendered spec 0001's flat Today/Recent lists — has no remaining call site once Story renders other_members directly through HeadlineCard. Check your understanding

Q1. Why does Story render no <details> element at all for a Story of one, rather than a disclosure that just opens onto an empty list?

Reveal answer

A disclosure implies there's something to reveal. Rendering one that opens onto nothing would be a UI element with no purpose, and would visually clutter the far more common case (a Story with no other members) for no benefit -- the length check gates whether the whole element exists, not just whether it starts open or closed.

Q2. Why does new Date("2026-09-16") risk displaying the wrong day, and why does manually splitting the string and using new Date(year, month - 1, day) fix it?

Reveal answer

A bare "YYYY-MM-DD" string is parsed as UTC midnight by Date's string constructor. Formatting that moment in the viewer's local timezone can land on the previous calendar day for anyone west of UTC. The local-time constructor takes year/month/day as plain numbers with no timezone reinterpretation at all, so the displayed day always matches the input's day, regardless of what timezone the browser happens to be in.

Q3. Why was HeadlineList deleted rather than kept around, even though nothing in this lesson strictly required removing it?

Reveal answer

Once Story renders other_members directly via HeadlineCard, HeadlineList has zero remaining call sites -- it's genuinely, verifiably dead code, not a component that might be needed again soon. This codebase's own convention is to delete code once you're certain it's unused rather than keep unused wrappers "just in case," since an unused component left behind is a maintenance cost with no offsetting benefit.
