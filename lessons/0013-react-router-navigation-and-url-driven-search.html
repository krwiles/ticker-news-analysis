React Router: navigation, and the data-loading pattern

Two things that were quietly missing since lesson 11: a way to actually get between the two pages, and a URL that means something.

Since lesson 11, / and /search both worked — but only if you typed the URL yourself. Nothing linked them, and /search only ever did anything after a manual form submit. Both get fixed here, for real, not just explained.

<Outlet />: the closest one-to-one match in the whole translation table

frontend/src/components/Layout.tsx is new — a nav bar plus one thing: 

export function Layout() {
  return (
    <div>
      <nav>
        <Link to="/">Status</Link>
        <Link to="/search">Search</Link>
      </nav>
      <Outlet />
    </div>
  );
}

<Outlet /> means "render whichever child route matched" — which is almost literally Angular's <router-outlet>, right down to the name. App.tsx nests both existing routes under it: 

<Routes>
  <Route element={<Layout />}>
    <Route path="/" element={<StatusPage />} />
    <Route path="/search" element={<SearchPage />} />
  </Route>
</Routes>

And <Link to="/search">, not a plain <a href="/search"> — the whole reason a router library exists. A plain anchor tag would trigger a full page reload (a fresh index.html, a fresh React app boot); Link intercepts the click and navigates client-side instead, which is provably true, not just claimed: StatusPage's 5-second poll interval doesn't reset when you navigate away and back through the nav.

The data-loading pattern: the URL is the actual source of truth

Before this lesson, /search only ever fetched in response to a form submit. SearchPage.tsx now uses useSearchParams so the URL drives it instead: 

const [searchParams, setSearchParams] = useSearchParams();
const urlTicker = searchParams.get("ticker");

useEffect(() => {
  if (urlTicker) {
    runSearch(urlTicker);
  }
}, [urlTicker]);

function handleSearch(ticker: string) {
  setSearchParams({ ticker: ticker.toUpperCase() });
  // the effect above picks up the resulting param change and fetches --
  // one fetch-triggering path, not two copies of it
}

Visit /search?ticker=AAPL directly — a shared link, a bookmark, browser Back/Forward — and it loads for real, with zero manual interaction. That's the actual "data-loading pattern" named in this lesson's scope: the route's own URL state drives what data loads, not just a click handler.

Worth being precise rather than overclaiming the Angular parallel: this project uses React Router's declarative mode (RESOURCES.md's own note), which has no built-in resolver-style route loader the way Angular's router does. useSearchParams + an effect is the idiomatic way to get the same outcome in declarative mode — a real analogy, not the same mechanism.

React Router's separate data mode does have real loaders — a different API this project doesn't use.

Case handling: uppercase on write, anything works on read

Submitting normalizes once (ticker.toUpperCase()) before writing the URL — so the URL always shows the canonical form. But visiting /search?ticker=aapl (lowercase, hand-typed or shared) still works, with no extra frontend code at all: search.py's endpoint already calls ticker.upper() before anything else happens server-side, so passing the raw param straight through to fetchSearch resolves correctly regardless of case. Verified with a real test rather than left as an assumption — SearchPage.test.tsx's "still functions when the URL's ticker is lowercase" asserts fetchSearch gets called with the untouched, lowercase value.

A real React gotcha: initialValue is a snapshot, not a binding

SearchBar's useState(initialValue ?? "") only reads initialValue once, at mount. If the URL's ticker changes later while the same SearchBar instance stays mounted (browser Back to a previous search, say), the input would keep showing the old ticker — a real, visible inconsistency with the results below it, unlike an Angular @Input(), which would keep reflecting the latest value automatically.

Fixed with React's own recommended pattern for exactly this — not an effect that syncs state, but a changing key that forces a clean remount: 

<SearchBar key={urlTicker ?? ""} initialValue={urlTicker ?? undefined} ... />

A different key means React treats it as a genuinely different component instance — the old one unmounts (stale state and all), a fresh one mounts with the new initialValue. See react.dev's own "Resetting state when a prop changes" — this is the case it's written for.

Check your understanding

Q1. Why doesn't submitting the exact same ticker twice in the search bar trigger a second fetch?

Reveal answer

Fetching is triggered by the URL's ticker param changing (the effect's dependency). Submitting an unchanged value calls setSearchParams with the same value, so the URL doesn't actually change, so the effect never re-fires. This is exactly why spec 0001 needs a separate Refresh button (lesson 14) -- re-fetching the *same* ticker on demand needs its own explicit trigger, not a side effect of resubmitting the search bar.

Q2. Why is key={urlTicker} the fix for the stale-input problem, rather than an effect that calls setTicker(initialValue) when initialValue changes?

Reveal answer

Both would work, but key is react.dev's own recommended approach for "reset a component's entire state when some external value changes" -- it lets the component's existing, already-correct mount-time initialization do the work, rather than adding a second, effect-driven path that duplicates what useState(initialValue) already does once.
