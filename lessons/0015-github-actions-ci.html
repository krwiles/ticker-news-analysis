Continuous integration with GitHub Actions

Arc 3 opens: wiring up tests that already pass, so they keep passing without you having to remember to run them.

A tech-stack audit (previous session) compared the original stack list against what's actually been used. GitHub Actions was named but never built — .github/workflows/ didn't exist until this lesson. Lowest-effort candidate of everything still unused: both test suites already exist and pass, this just reproduces that in CI.

Three jobs, not one — and why that split matters

.github/workflows/ci.yml defines three independent jobs, each running on its own fresh runner, in parallel by default: 

jobs:
  frontend-tests: ...
  backend-tests: ...
  docker-build: ...

This mirrors the project's own directory split (frontend/, backend/, one shared Dockerfile) rather than one long job doing everything sequentially. The practical payoff: if only the frontend breaks, you see that immediately in the job list — you're not waiting on an unrelated backend job to finish first, and a red X next to "frontend-tests" tells you exactly where to look before you've even opened the log.

Service containers: a real Postgres, without touching docker-compose.yml

backend/tests/conftest.py has said since lesson 10: "Tests run on the host... never inside a container... everything here talks to Postgres via localhost." A GitHub Actions service container is built for exactly this shape — a sidecar Postgres the job's own steps reach at localhost:5432, with no compose file involved at all: 

services:
  postgres:
    image: postgres:17-alpine
    env:
      POSTGRES_USER: ticker
      POSTGRES_PASSWORD: ticker
      POSTGRES_DB: ticker_test
    options: --health-cmd pg_isready --health-interval 5s ...

Pinned to postgres:17-alpine deliberately — the exact same image docker-compose.yml's real db service uses, not an arbitrary different version. The user/password/database names match conftest.py's own documented default connection string exactly, so the job needs zero environment-variable overrides to make the two agree.

Pin what has no lockfile; don't bother pinning what does

Two very different choices sit right next to each other in the backend-tests job, worth contrasting directly: 

- uses: astral-sh/setup-uv@v4
- run: curl -fsSL -o /usr/local/bin/dbmate \
    https://github.com/amacneil/dbmate/releases/download/v2.35.1/dbmate-linux-amd64

uv gets no specific version pin — uv.lock already pins every actual Python dependency precisely; uv's own version matters far less for reproducibility, since it's just the tool reading an already-locked manifest. dbmate is different: it has no lockfile equivalent anywhere in this repo — nothing else records which version applied these migrations last, or guarantees a newer one behaves identically. Pinned to 2.35.1, the exact version verified locally, specifically because nothing else here provides that guarantee.

A YAML gotcha worth naming: working-directory composition isn't obvious

The first draft of backend-tests used a job-level defaults.run.working-directory: backend, then tried to override it per-step for the dbmate command (which needs the repo root, since db/migrations/ is relative to that, not to backend/). Whether a step's own working-directory composes with or fully replaces a job-level default isn't something worth guessing at and hoping — get it wrong and dbmate silently looks in the wrong place for migrations, or worse, half-applies something confusing. Fixed by removing the job-level default entirely and setting working-directory explicitly on the one step that needs it (uv run pytest), leaving the dbmate steps to use the workspace root implicitly. Unambiguous beats clever.

What this lesson deliberately doesn't do

No linter is wired in — none exists on either side of this repo yet; that's its own decision (which tool, which rules), not something to slip in unannounced while "just" setting up CI. No live end-to-end smoke test either — bringing up all five docker-compose services and hitting a real /api/search would need a real Finnhub API key as a GitHub secret and meaningfully more machinery. The existing 17 backend + 38 frontend tests, all of them mocked at their real boundaries (respx, vi.mock), are this pass's actual regression coverage — CI's job is to run them reliably, not to replace them with something bigger.

Check your understanding

Q1. Why does dbmate get a specific version pin in this workflow while uv doesn't?

Reveal answer

uv.lock already pins every real Python dependency precisely -- uv's own version mostly just reads that lockfile faithfully. dbmate has no equivalent lockfile anywhere in this repo recording which version last applied migrations, so nothing else guarantees a different dbmate version would behave identically -- pinning it here is the only reproducibility guarantee that exists for it at all.

Q2. Why does the Postgres service container use postgres:17-alpine specifically, and the exact ticker/ticker/ticker_test credentials, rather than whatever was convenient?

Reveal answer

To match two things exactly rather than introduce a third, different environment: docker-compose.yml's real db service image (so CI's Postgres version matches what actually runs everywhere else), and conftest.py's own already-documented default connection string (so the job needs zero environment-variable overrides for the two to agree).
