Lesson 29 of 30 · ticker-news-analysis stack (sentiment arc — Arc 5 — capstone)

Frontend: sentiment UI + polling

A poll loop that stops itself, one shared pill component instead of four visual states, and a Story wrapper gated on member count, not on whether the data happens to be there.

Capstone of this arc, same role lesson 22 played for arc 4: spec 0005 is fully built after this, not just modeled. Pure frontend — no backend or API changes, everything consumed here already shipped in lessons 26 and 28.

A poll loop that mirrors StatusPage's shape, but not its lifetime

StatusPage polls forever, from mount, with an immediate first tick — there's always fresh data to show and no reason to ever stop. Sentiment is different: it's a fire-and-forget job with a real endpoint (a genuine window where a poll is worth making), and a real end (once it resolves, polling forever afterward would just be waste). The fix uses React's own effect-cleanup mechanics instead of a manual "stop polling" flag: 

useEffect(() => {
  if (!results || results.sentiment !== "processing") {
    return;
  }
  let cancelled = false;
  const id = setInterval(poll, SENTIMENT_POLL_INTERVAL_MS);
  return () => {
    cancelled = true;
    clearInterval(id);
  };
}, [results?.ticker, results?.sentiment]);

Keying the effect on results.sentiment itself is the trick: every time sentiment changes (including the very change a poll tick just caused), the effect re-runs — cleanup tears down the old interval, and the guard decides fresh whether a new one is worth creating. Once sentiment is no longer "processing", that guard returns early and nothing gets scheduled. No stop flag, no manual bookkeeping — the interval's existence is the "am I still polling" state.

Merge, not replace — the consequence ADR 0014 flagged two lessons ago

/api/search/status deliberately returns a narrower shape than /api/search — just {sentiment, days}, no ticker/status/providers/ grouping (it never re-runs the fetch, so it has nothing new to say about them). A poll tick that called setResults(status) directly would silently wipe those other fields from the screen the moment sentiment finished resolving: 

setResults((prev) => (prev ? { ...prev, sentiment: status.sentiment, days: status.days } : prev));

Spreading the previous state and overwriting only the two keys this endpoint actually knows about is what keeps the rest of the page stable across every poll tick.

One shared pill, two visual buckets — not four

A headline's sentiment can be unresolved for three different reasons — not yet attempted, skipped (no API key), or a real error — plus one resolved state with a real enum. That's a real four-way distinction, but it doesn't belong on every single headline's own pill. The new page-level SentimentStatus component (mirroring GroupingStatus exactly) explains the why once, for the whole page. The per-item SentimentPill only needs two buckets: 

if (enumValue === null || score === null) {
  return <span className="... text-slate-400">Pending</span>;
}
return (
  <span className={`... ${COLOR[enumValue]}`}>
    {gloss ? `${gloss} · ${score}` : `${enumValue} · ${Math.round(score)}`}
  </span>
);

That same component is shared by HeadlineCard (which always has a gloss) and Story's own aggregate pill (which never does — a Story average is just a number, no LLM gloss attached to it), so the two call sites can't quietly drift into different visual languages for the same underlying idea.

The Story wrapper is gated on member count, not on whether the data exists

Lesson 28's own live verification already showed something easy to miss here: the backend returns a real, if trivial, sentiment_average even for a Story of exactly one member — it's just that member's own score, reflected back. CONTEXT.md is explicit that the aggregate concept only applies once there's more than one member to average, so the frontend gate has to match that definition, not the raw presence of the field: 

const isMultiMember = story.other_members.length > 0;
if (!isMultiMember) {
  return <div>{primaryCard}</div>;
}
// ...outer card, "Story" pill, aggregate SentimentPill...

Checking sentiment_average !== null instead would have been wrong in a subtle way: a real single-member Story would occasionally show a pointless "Story" wrapper around its one and only headline, the moment that headline's own sentiment happened to resolve.

A test bug caught by the tests themselves, not by inspection

The first version of the "multi-member Story shows a Pending aggregate pill" test left both Story members with their default, unresolved sentiment. getByText("Pending") failed — correctly — because there were two Pending pills on the page: the aggregate's, and the still- unresolved member's own headline-level pill (rendered inside the closed <details>, present in the DOM even while collapsed). Fixed by giving both members a real resolved score in that test, so the only remaining "Pending" text is unambiguously the aggregate's. A real, if small, reminder that a shared component means a test has to think about every place it renders, not just the one under test.

Verification, and an honest gap

Check your understanding

Q1. Why is the poll useEffect keyed on [results?.ticker, results?.sentiment] instead of [] like StatusPage's?

Reveal answer

StatusPage polls forever, so it only ever needs to subscribe once, at mount. Sentiment polling needs to stop once resolved -- keying the effect on sentiment itself means every status change re-runs the effect, tearing down the old interval via cleanup and only creating a new one if the guard (still "processing") is still true. The interval's own existence becomes the "still polling" state, with no separate flag to keep in sync.

Q2. Why does a Story of exactly one member never show the outer "Story" wrapper, even though the backend gives it a real sentiment_average?

Reveal answer

The aggregate concept (CONTEXT.md) only means something once there's more than one member to average -- a lone member's "average" is just its own score reflected back, not a new fact. The frontend gates on other_members.length, not on whether sentiment_average happens to be non-null, so a single-member Story never gets a pointless wrapper around its one headline just because that headline's sentiment resolved.
