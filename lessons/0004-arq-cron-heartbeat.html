ARQ's cron/heartbeat mechanism

A process with no server has to prove it's alive by pushing, not by answering.

What ARQ actually is

ARQ is a Redis-backed job queue for Python's asyncio — the thing that runs code later or on a schedule, outside the request/response cycle FastAPI handles. Think of it as the asyncio-native, Redis-only sibling of Celery: fewer moving parts, one broker (Redis, which this project already runs), no separate message-broker service to stand up.

backend/src/ticker_backend/worker.py

class WorkerSettings:
    cron_jobs = [cron(heartbeat, second=set(range(0, 60, 5)))]
    redis_settings = RedisSettings.from_dsn(settings.redis_url)

WorkerSettings is never instantiated anywhere in this codebase — it's a plain class used purely as a bag of config attributes. The command arq ticker_backend.worker.WorkerSettings (the worker service's compose command:, from lesson 1) is ARQ's own CLI: it imports that dotted path, reads the class attributes off it, and starts a worker process configured accordingly.

A "config as a bare class" convention shows up a lot in Python (Django settings modules do the same thing) — there's no framework magic instantiating it, ARQ's CLI just reads class attributes directly.

Cron scheduling is wall-clock, not "every N seconds since start"

cron(heartbeat, second=set(range(0, 60, 5))) means: run heartbeat whenever the wall-clock second is 0, 5, 10, 15, ... 55 — every real-world second that's a multiple of 5. That's a genuinely different thing from "wait 5 seconds after the worker starts, then repeat." If the worker starts at :02, the first heartbeat fires at :05 — three seconds later, not five — and every heartbeat after that lands on a clean multiple of 5, regardless of exactly when the process happened to boot.

This matters beyond this one heartbeat: any future cron job in this project (say, "fetch news every hour on the hour") gets the same wall-clock alignment for free, which a naive while True: sleep(3600) loop would not give you — that drifts based on exactly when the process started.

The job function, and ctx

async def heartbeat(ctx: dict) -> None:
    await ctx["redis"].set(WORKER_HEARTBEAT_KEY, str(time.time()))
    log.info("worker.heartbeat")

Every ARQ job function takes one argument, ctx — a dict ARQ builds and hands to each job, carrying (among other things) an already-connected Redis client at ctx["redis"]. That client is an ArqRedis, which is a subclass of the same redis.asyncio.Redis lesson 3 used — so it supports ordinary commands like .set() directly, on top of whatever ARQ itself needs it for (enqueueing and tracking jobs).

Worth contrasting directly with lesson 3's check_redis(), which opens a brand-new Redis connection on every call. heartbeat() does the opposite — it reuses the one connection ARQ already manages for the whole worker process. That's the "production-shaped" version of the pattern lesson 3 flagged as a simplification.

Same library, two different lifetimes — short-lived-per-request vs long-lived-per-process. Both are real, correct patterns for their situation.

Why a heartbeat, not a health check

/health (lesson 3) works by asking — the api container reaches out to the database and Redis and waits for an answer. That only works because those two have something listening. The worker has no server at all: nothing to connect to, no port to ask. So it inverts the relationship — instead of being asked "are you alive," it periodically announces "I was alive as of this timestamp," and leaves interpreting that announcement to whoever's asking (the api container's check_worker(), which reads the timestamp and reasons about its age).

Real log output from the running container:

worker-1  | 17:47:30:   1.01s → cron:heartbeat()
worker-1  | {"event": "worker.heartbeat", "timestamp": "2026-09-04T17:47:30...", "level": "info"}
worker-1  | 17:47:30:   0.00s ← cron:heartbeat ●
worker-1  | 17:47:35:   1.01s → cron:heartbeat()

Note the real gap: 17:47:30 to 17:47:35 — five seconds apart, landing on the clean multiples the cron schedule promised.

Check your understanding

Q1. The worker container starts at 14:00:03. At what wall-clock time does the first heartbeat fire?

Reveal answer

14:00:05 — two seconds after start, the next clean multiple of 5, not 14:00:08 (which "5 seconds after start" would imply).

Q2. Why can heartbeat() just call ctx["redis"].set(...) directly, while check_redis() in lesson 3 has to create a client first with Redis.from_url(...)?

Reveal answer

ARQ already builds and manages a long-lived Redis connection for the whole worker process and hands it to every job via ctx["redis"]. The api container's health check has no equivalent long-lived client sitting around, so it opens one itself, per call.
