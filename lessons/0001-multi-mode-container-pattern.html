The multi-mode container pattern

One image, three jobs — why this repo doesn't have a "ui" repo and an "api" repo.

The shape

Open docker-compose.yml and you'll see five services, but only one build: . line. db and redis pull public images. ui, api, and worker all build from the exact same Dockerfile — same dependencies, same source code, same everything. What makes them different containers isn't the image, it's one environment variable: APP_MODE.

This is a real trade-off, not a shortcut. See docs/adr/0001-single-image-multi-mode-containers.md in the repo for the full reasoning and the alternative that was rejected.

An ADR (Architecture Decision Record) is a short file that captures why a hard-to-reverse technical choice was made — so nobody re-litigates it, or "fixes" it, six months later without the context.

docker-compose.yml (trimmed)

services:
  api:
    <<: *app
    environment:
      APP_MODE: api
    ports:
      - "8000:8000"

  ui:
    <<: *app
    environment:
      APP_MODE: ui
    ports:
      - "3000:8000"

  worker:
    <<: *app
    environment:
      APP_MODE: worker
    command: ["arq", "ticker_backend.worker.WorkerSettings"]

<<: *app is a YAML anchor — it pastes in the shared build: . and depends_on block defined once at the top of the file, so the three services don't repeat it three times. Purely a YAML trick, nothing Docker-specific.

How one image becomes three programs

The Dockerfile has two stages: a Node stage that builds the React app into static files, and a Python stage that installs FastAPI/ARQ and copies those static files in. The result is one image with everything in it — Python code, Python dependencies, and a prebuilt frontend — sitting there unused until something decides which role to play.

backend/src/ticker_backend/main.py

def create_app() -> FastAPI:
    app = FastAPI(title="ticker-news-analysis", version="0.1.0")

    if settings.app_mode == "api":
        app.include_router(health_router)         # the full JSON aggregate
    else:
        app.include_router(ui_health_router)      # a trivial self-check only
        app.frontend("/", directory=STATIC_DIR)   # serve the React build

    return app

Each branch gets a genuinely different router now, not the same one twice — lesson 2 covers exactly why.

worker mode doesn't even run this file — the compose command: override points it at arq ticker_backend.worker.WorkerSettings instead, a completely different entrypoint that never creates a FastAPI app at all. Same image, same Python environment, different program run inside it.

Lesson 4 covers what WorkerSettings actually does.

So "mode" isn't one mechanism — it's two, stacked: api vs ui is a branch inside main.py based on settings.app_mode (itself read from the APP_MODE env var via pydantic-settings); worker is a different entrypoint entirely, chosen by compose's command: before Python code even runs.

Why bother — why not three separate images?

The honest cost: the ui container ships with a full Python runtime it will never use to render a single JSON response. A bare nginx-serving-static-files image would be smaller and simpler for that one job.

What buys that back: one Dockerfile, one build pipeline, one image tag. The UI and the API can never drift onto different dependency versions, because they're not just similar — they're the same install. That matters more on a team shipping fast than it does for a single static-assets image being marginally leaner.

Check your understanding

Q1. If you changed a Python dependency version, how many images would need rebuilding — and which compose services would restart?

Reveal answer

One image (the shared build). All three services that use it — ui, api, and worker — would restart, since they're all just that one image running differently.

Q2. worker mode is picked by a compose command: override. ui/api mode is picked a different way — how?

Reveal answer

By reading the APP_MODE env var inside main.py itself (settings.app_mode), and branching on it — both still run the same uvicorn command, just with different app behavior once Python code executes.
