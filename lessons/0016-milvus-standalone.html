Milvus, standalone

Arc 4 opens: three new containers, no app logic yet — and two real bugs found live before a single line of grouping code exists.

Milvus is the one item left on the original stack list (MISSION.md) with zero lessons behind it. This one proves the infra works — a real collection, real insert/search via pymilvus — with nothing wired into providers.py yet. See docs/specs/0002-daily-story-grouping.md for what it's actually for.

Fetched the real reference config, not the remembered one

Standalone Milvus needs two sidecars — etcd for metadata, MinIO for object storage — neither talked to directly by this app, both just giving milvus somewhere to keep state. Rather than approximate that shape from memory, the actual current milvus-io/milvus reference compose file got fetched directly — exact image tags, environment variables, healthchecks. Same "never trust parametric knowledge" discipline this whole project has used for EDGAR/Finnhub response shapes, applied to infrastructure config instead of an HTTP response.

Two deliberate departures from copying it verbatim: named Docker volumes instead of the reference's bind-mounts (matching this file's own db-data convention), and no separate networks: block — that reference declares one because it's a *standalone* file with nothing else in it; here, etcd/minio/milvus join the same default network db/redis/api/ui/worker already share.

Bug #1: the reference config itself was already broken

docker compose up on the fetched config failed immediately: pull access denied for minio/minio, repository does not exist. Not a typo — MinIO archived its open-source edition and pulled every minio/minio image from Docker Hub, a change that finished landing this exact week. The fix, cross-checked against Milvus' own maintainers hitting the identical bug: same tag, different registry — 

quay.io/minio/minio:RELEASE.2024-05-28T17-19-04Z

Verified by actually pulling it before touching the compose file, not just trusting the GitHub issue. Worth sitting with: a reference config from an official source can still be stale by the time you use it — "verify against reality" doesn't stop applying just because the source looks authoritative.

Bug #2: a healthy container proved less than it looked like

With all three containers reporting healthy, the first pymilvus smoke test inserted three vectors and searched for the nearest neighbor — and got back zero results. Not an error, just silently empty. Debugging isolated it precisely: 

client.insert(collection_name=..., data=[...])
client.get_collection_stats(collection_name=...)  # {'row_count': 0}  <- still zero!

client.flush(collection_name=...)
client.get_collection_stats(collection_name=...)  # {'row_count': 1}  <- now it's there

insert() doesn't make data searchable on its own — it lands in memory/WAL, not a sealed, queryable segment, until explicitly flushed. This isn't just a smoke-test footnote: it's a real constraint on lesson 19's actual design. When a new headline's embedding gets inserted as a fresh Story's primary, that primary needs to be searchable by whatever headline comes next — which means flush() has to be part of that flow somewhere, not a one-off call in a throwaway script. Flagged here for lesson 19 to actually solve, not solved now.

Real proof, once both bugs were fixed

# three vectors: "alpha", "beta" (deliberately dissimilar), "alpha-near-duplicate"
Nearest neighbors to alpha:
  id=1 label=alpha                 distance=1.0000
  id=3 label=alpha-near-duplicate  distance=0.9970

beta correctly never shows up — a small, deliberate preview of exactly the mechanic spec 0002 actually needs: given one vector, find its real near-duplicates, not everything in the collection.

Why worker alone waits on Milvus, not api/ui too

db/redis are shared across all three app containers via one &app anchor — simplicity over precision, since ui doesn't actually need either but inherits the dependency anyway. Milvus breaks that pattern deliberately: its healthcheck has a real 90-second start_period, and only worker will ever call it (starting lesson 18). Making it shared would slow down api/ui startup for a dependency they'll never use. Fixed by extracting depends_on into its own named anchor (&app-depends-on), the same move already applied to environment — worker merges it and adds milvus, api/ui keep using the shared anchor unchanged. Verified live, not just read from the YAML: on docker compose up, api/ui started the moment db/redis were healthy; worker visibly waited on milvus too.

Check your understanding

Q1. Why did the first smoke test's search come back empty even though the insert call itself reported success?

Reveal answer

Milvus' insert() lands data in memory/WAL, not a sealed segment search actually queries -- it isn't searchable until flushed. get_collection_stats() confirmed this precisely: row_count stayed 0 after insert, and only became 1 after an explicit flush() call.

Q2. Why does worker get its own depends_on block instead of just adding milvus to the shared &app anchor db/redis already use?

Reveal answer

Milvus' healthcheck has a real 90-second start_period, and only worker will ever call it. Sharing the dependency the way db/redis are shared (simplicity over precision, since even ui inherits them despite not needing either) would make api/ui wait on a service they'll never use -- worth the small extra anchor-extraction complexity to avoid.
