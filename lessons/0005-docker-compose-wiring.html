How docker-compose wires it all together

Networking, startup order, and persistence — the parts of the skeleton that aren't Python or React at all.

Service names are hostnames

Recall config.py's default: postgresql+asyncpg://...@db:5432/.... db is not a placeholder — it's the literal hostname the api/ui/worker containers use to reach Postgres, and it resolves because compose puts every service in the file on one shared network and registers each service's name as its DNS name on that network automatically. No IP addresses, no manual network config — redis://redis:6379 works for the identical reason.

This only works between containers. From your host machine's browser, db means nothing — that's why the compose file also maps 5432:5432 to the host, a separate concern from the container-to-container networking above.

Two different audiences, two different addressing schemes: containers talk to each other by service name; your host talks to containers by localhost:<mapped port>.

Port mapping: HOST:CONTAINER

docker-compose.yml

ui:
    ports:
      - "3000:8000"
  api:
    ports:
      - "8000:8000"
  worker:
    # no ports: block at all

Both ui and api run the identical uvicorn command internally, listening on container port 8000 (lesson 1). The left side of "3000:8000" is what your machine sees; the right side is what the container itself is bound to. That's the entire reason localhost:3000 and localhost:8000 reach two different containers despite both containers listening on the same internal port — the host-side mapping is what actually differs. worker has no ports: block at all: nothing outside the compose network ever needs to reach it directly, so nothing is exposed.

Startup order isn't file order — it's depends_on + real healthchecks

db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10

x-app: &app
  depends_on:
    db:
      condition: service_healthy
    redis:
      condition: service_healthy

pg_isready is Postgres's own CLI tool for "can this server actually accept connections yet" — genuinely different from "is the container running," which can be true seconds before Postgres has finished initializing. condition: service_healthy on api/ui/worker (inherited from the x-app anchor lesson 1 introduced) means compose won't even start those containers until db's healthcheck passes — not "started," healthy.

This is visible directly in compose's own startup log:

Container db-1     Starting
Container redis-1  Starting
Container db-1      Waiting
Container redis-1   Waiting
Container db-1      Healthy
Container redis-1   Healthy
Container api-1     Starting   ← only now, after both report Healthy
Container worker-1  Starting
Container ui-1       Starting

Without this, the api container could boot, try its first database connection during startup, and crash before Postgres finished initializing — a real, common Docker Compose failure mode this project structurally avoids.

Persistence: why db has a volume and redis doesn't

services:
  db:
    volumes:
      - db-data:/var/lib/postgresql/data
  redis:
    # no volumes: block

volumes:
  db-data:

db-data is a named volume — storage that outlives the container. Stop and recreate the db container (docker compose up again after a rebuild, say) and the data is still there, because the volume, not the container, is what actually holds it. redis gets no such volume on purpose: everything it's storing right now (the worker's heartbeat key) is meant to be disposable — losing it just means the status page shows "worker: error" for a few seconds until the next heartbeat, not a real problem worth persisting through restarts.

The env vars come from .env, automatically

${POSTGRES_USER}, ${POSTGRES_PASSWORD}, ${POSTGRES_DB} throughout the file aren't set anywhere in docker-compose.yml itself — compose reads a .env file in the same directory automatically and substitutes them in, which is also why .env is gitignored (secrets) while .env.example (no real secrets, just the shape) is committed.

Check your understanding

Q1. You curl db:5432 from your host machine's terminal (not from inside a container). Does it work?

Reveal answer

No — db only resolves on the compose network, between containers. From the host you'd need localhost:5432, which works only because of the explicit port mapping in the compose file.

Q2. You run docker compose down then docker compose up again. Is the worker's last heartbeat still in Redis? Is last week's Postgres data still there?

Reveal answer

The heartbeat is gone (Redis has no volume — a fresh container starts empty). The Postgres data survives, because it lives in the db-data named volume, not in the container itself.
