Single-flight jobs per ticker

What actually happens when two requests want the same fetch at once — measured, not guessed — and why the fix shares one run instead of making the second request wait its turn.

Not a planned lesson, and not a bug report — a question asked ahead of the code: "if two requests hit the same fetch before the first finishes, does the second overwrite the first?" The reason for asking was the road ahead (user accounts, several people searching, a background job refreshing tickers on its own). This lesson answers it with evidence from the real stack, then closes the gap.

Prove the problem before fixing it

Reading the code suggested three things might go wrong. Before changing anything, two simultaneous curl /api/search?ticker=ORCL calls (a ticker the database had never seen) tested each guess.

Run 1 — a brand-new ticker. The two requests disagreed: one came back success, the other complete_failure with no providers and no stories. The worker log showed why:

fetch_headlines_job failed, IntegrityError: ... UniqueViolationError:
duplicate key value violates unique constraint "companies_pkey"

Two sentiment_job('ORCL') runs also overlapped for about 65 seconds each. The Story aggregates, though, came out correct (131 of 131 Stories matched, 112 = 112). That looked reassuring — and turned out to be luck, as the next run showed.

Run 2 — same ticker, its sentiment reset, same two calls. Two fetch jobs and two overlapping sentiment jobs (58.4s and 64.1s), this time over fully grouped headlines:

SUM(stories.sentiment_score_count) = 224
headlines actually at sentiment_status = 'ok' = 112
Stories inflated: 105 of 131   (26 matching, 0 undercounted)

Every score was folded into its Story's running average twice. And it's permanent: an ok headline is never re-scored, so nothing ever corrects the count. The guess from reading the code was right — but only Run 2 proved it, and Run 1 is the reminder of why one lucky run isn't proof of safety.

Why headline upserts were already safe

The worst-sounding scenario — both fetches inserting the same headlines — is the one Postgres already handles: 

stmt = pg_insert(Headline).values(**headline)
stmt = stmt.on_conflict_do_update(index_elements=["url"], set_={...}).returning(
    Headline.id, literal_column("(xmax = 0)").label("was_inserted")
)

ON CONFLICT is a single statement Postgres arbitrates itself: the second writer waits for the first's row lock, then takes the "update" path on a row that now exists. The xmax = 0 column tells exactly one of them its row was genuinely new, so only one job groups it. Nothing gets overwritten that matters — story_id and the sentiment columns aren't in the set_ list.

Two races that weren't safe, and the names for them

Check-then-act. get_company checks the cache, misses, fetches SEC's list, then calls session.merge(Company(...)). merge is two steps — a SELECT, then an INSERT — with a gap between them. Both jobs looked during the gap, both saw "no row", both inserted, and the second hit the primary key. That's Run 1's crash. Note the contrast with the upsert above: one atomic statement versus two steps with a gap.

Read-modify-write. Story.record_sentiment() reads the current count and average into Python, computes the new values, and writes them back: 

new_count = self.sentiment_score_count + 1
self.sentiment_average += (score - self.sentiment_average) / new_count
self.sentiment_score_count += 1

Called once per headline that's fine. Called twice per headline by two jobs, you get Run 2's 224. (Lesson 30's sequential-writes comment protects two headlines within one job; nothing protected two jobs from each other.)

A semaphore serializes. What you want is single-flight.

The natural instinct is "a semaphore per ticker" — lesson 26 taught Semaphore(20), and a semaphore of size 1 keyed by ticker is a lock. It would stop the overlap, but look at what the second request then does: waits, then runs the entire fetch again, calling EDGAR and Finnhub for data the first run just stored. Two requests, two full runs, just not at the same time.

Single-flight (also called request coalescing) does better: the second caller notices a run is already in progress and waits for that run's result. One fetch, two callers, one shared answer. If you know Angular, it's in the spirit of sharing one in-flight observable among several subscribers with shareReplay rather than letting each subscriber start its own HTTP call.

That's also the shape a future background refresher wants. If it refreshes AAPL while a user searches AAPL, the user should simply join the refresh already running, not trigger a second one.

ARQ already has the atomic part built in

Every ARQ job has an ID; by default it's random. If you pass your own, enqueue_job returns None instead of a Job when that ID is already queued, running, or has a stored result. Redis checks-and-claims the ID in one atomic step (a WATCH/MULTI transaction), so it holds across any number of api and worker processes. The whole idea is one small function in the new jobs.py: 

async def enqueue_or_join_fetch(arq_redis, ticker, job_factory=Job):
    job_id = fetch_job_id(ticker)                    # "fetch_headlines:AAPL"
    job = await arq_redis.enqueue_job("fetch_headlines_job", ticker, _job_id=job_id)
    if job is None:                                  # ID taken: someone else's fetch is in flight
        job = job_factory(job_id, redis=arq_redis)   # a handle to *their* job
    return job                                       # either way: await job.result(...)

This is why the coordination lives in Redis and not an asyncio.Lock. A lock lives in one process's memory. ADR 0014 concluded "one worker process is enough" — true today, but a background refresher, a second worker, or the api container calling in would each be a place a memory lock can't see. Redis is the one place all of them already share.

The sentiment job uses the same trick with sentiment:AAPL, but nobody awaits it (it's fire-and-forget), so a None is simply ignored: a job for that ticker is already running.

Two ARQ details you only find by reading its source

Results must be kept — briefly. A joiner calls Job.result(). If the job finishes and no result was stored, and it's no longer in the queue, ARQ raises ResultNotFound — the joiner would get an error instead of an answer. But ARQ's default is to keep results for an hour, and enqueue_job returns None while a result exists — so with the default, every Refresh would silently return an hour-old result. The fix is the middle path, set where the worker registers the job: 

functions = [
    func(fetch_headlines_job, keep_result=FETCH_RESULT_TTL_SECONDS),   # 5 seconds
    func(sentiment_job, keep_result=0),                                # nobody reads it
]

A side effect worth knowing: for 5 seconds after a fetch finishes, a new request shares its result instead of running a fresh one. That's a small deliberate cooldown, and it's a useful guard against hammering the providers.

Why there's no _expires. ARQ lets you give a job an expiry, which sounds like a safety net against a stuck job blocking a ticker forever. But sentiment jobs run 60-100+ seconds; an expiry shorter than that would let a second sentiment job start mid-run, reopening the exact overlap this lesson closes. A hung job is already bounded by ARQ's 300-second job_timeout, and a crashed worker's job just gets retried when a worker returns.

Testing the join path without a Redis

enqueue_or_join_fetch takes job_factory=Job as a parameter — the same dependency-injection habit as milvus=None in ADR 0012. Tests hand it a fake, and a small fake Redis that mimics the one ARQ rule that matters (first enqueue of an ID wins, later ones get None). The key test fires two callers with asyncio.gather and asserts exactly one real enqueue and one shared result. To be sure the tests could actually fail, three things were deliberately broken one at a time — dropping .upper() from the ID, making the join return None, setting fetch's keep_result=0 — and the right tests went red each time. 78 tests became 86.

What tests with fakes can't prove is that ARQ really behaves that way. That's what the live checks below are for.

After the fix, same procedure

ORCL's sentiment reset again, the same two simultaneous requests, stack rebuilt with the change:

  • Both responses success, identical providers — no more one-fails-one-succeeds.
  • The worker ran one fetch_headlines:ORCL job and one sentiment:ORCL job — the deterministic IDs now appear in ARQ's own log lines.
  • SUM(sentiment_score_count) = 112 against 112 ok headlines; 0 of 131 Stories inflated (was 224 vs 112, and 105 inflated).
  • A request immediately after another returned in 11 ms with no new fetch (it shared the kept result); a request 7 seconds later ran a genuinely new one.
  • Simultaneous AAPL and MSFT searches started their fetches in the same second and overlapped — only same-ticker requests coalesce.

A bug the baseline found that this doesn't fix

Remember Run 1's lucky-correct aggregates? The reason is a separate problem. search() enqueues the sentiment job even when the fetch failed or timed out, so a sentiment job can start while a fetch is still grouping in the background. Its headlines are loaded with story_id = None, and _persist_result skips the Story aggregate for those — so their scores never reach it, and since ok is never re-scored, never will. Single-flight doesn't change that. It's recorded in plan 0031's out-of-scope list as its own future fix — noticing it and writing it down, rather than quietly widening this lesson, is the same discipline as the URL-attribution note in NOTES.md.

Check your understanding

Q1. Why is the headline ON CONFLICT upsert safe under concurrency, while get_company's session.merge() crashed?

Reveal answer

ON CONFLICT is one atomic statement that Postgres arbitrates: the second writer waits for the first's row lock, then takes the update path on a row that now exists. merge() is two separate steps, a SELECT and then an INSERT, with a gap between them. Both jobs ran their SELECT inside that gap, both saw "no such company", both INSERTed, and the second one hit the primary key. That's check-then-act.

Q2. Why can't the fetch job use keep_result=0? And why not just leave ARQ's one-hour default?

Reveal answer

A joiner waits on Job.result(). If the job finishes with no stored result and is no longer in the queue, ARQ raises ResultNotFound, so a caller who joined just before completion would get an error, not an answer. The one-hour default fails the other way: enqueue_job returns None for as long as a result exists, so every Refresh would join a finished job and return an hour-old result. A few seconds covers both: long enough for joiners to collect it, short enough that the next real search runs fresh.

Q3. A background refresher is planned. Why would a per-ticker asyncio.Lock inside the worker be the wrong tool for coordinating it with user searches?

Reveal answer

A lock lives in one process's memory, so it only coordinates code inside that process. The api container, a second worker, or a cron job in another process can't see it. It also serializes rather than shares: the second caller waits, then repeats the whole fetch. A deterministic job ID in Redis is visible to every process, and joining the in-flight job gives both callers one result from one fetch.

Q4. In Run 1 the Story aggregates came out correct even though two sentiment jobs overlapped. Why doesn't that mean the overlap was safe?

Reveal answer

The first job started before the winning fetch had finished grouping, so its headlines still had story_id = None and it skipped the aggregate update entirely. Only the second job folded scores in, so each was counted once, by timing luck. Run 2, with grouped headlines, showed the real behavior: every score counted twice. One passing run can't show that a race is safe; only the interleaving that happened to occur is proven.
