Lesson 21 of 21 · ticker-news-analysis stack (infra arc — Arc 4)

/api/search reshaped for N days

Spec 0002's last undesigned piece: replacing a fixed Today/Recent split with a variable list of days, each holding Stories instead of flat headlines.

A breaking API change, made deliberately rather than rolled out gradually — the first time this arc has done that. Everything else about this lesson (the reshape logic itself) is a pure-function extension of the pattern split_today_recent already established.

Two decisions before any code — recorded in ADR 0013

Every earlier lesson in this arc shipped non-breaking: a nullable column, an unused table, an additive grouping field. This one genuinely can't be additive without real cost — carrying both today/recent and a new days field in parallel would mean writing and testing two reshaping paths for a frontend that's about to be rebuilt anyway (lesson 22). Decision: replace the shape now, accept that the running frontend breaks until lesson 22 catches up. This is a personal project with no other users and the two lessons are built back to back — a real trade-off, made deliberately, not stumbled into.

Second decision: how many days does "one list per day" actually mean? A rigid 7-day scaffold would pad the response with empty buckets on the common case (a ticker with sparse news). Chosen instead: Today is always present, even with zero Stories — "nothing happened today" is a real, useful signal, the same one spec 0001's own empty "Today" section already showed. Every earlier day only appears if it actually has at least one Story.

The reshape is still a pure function — just building a tree, not two flat lists

/api/search already pulls the full flat list of matching headlines from Postgres in one query. Nothing about that changed. The reshape — grouping headlines into Stories, then bucketing Stories into days — replaces split_today_recent, but keeps its exact shape: a pure function, now passed in as a parameter rather than called internally, so every DST/Eastern-boundary case from lesson 10 stays testable without waiting for real midnight.

backend/src/ticker_backend/search.py

def build_daily_view(headlines: list[Headline], now: datetime) -> list[dict]:
    today_date = now.astimezone(EASTERN).date()

    by_day: dict = {}
    for headline in headlines:
        day = headline.published_at.astimezone(EASTERN).date()
        by_day.setdefault(day, []).append(headline)
    by_day.setdefault(today_date, [])  # Today is always present, even empty

    days = []
    for day in sorted(by_day.keys(), reverse=True):
        stories = _group_into_stories(by_day[day])
        stories.sort(key=lambda story: story["primary"]["published_at"], reverse=True)
        days.append({"date": day.isoformat(), "is_today": day == today_date, "stories": stories})
    return days

One implementation choice worth naming: headlines are bucketed into days first, then each day's bucket is grouped into Stories independently — not the other way around (group into Stories, then bucket by the primary's day). Both give the same answer, since a Story's members always share one Eastern day by construction (ADR 0006's day-scoping). But bucketing first doesn't have to rely on that invariant holding — it just reflects each headline's own real day, regardless.

A null story_id must become its own Story, not disappear or merge

ADR 0012 made grouping degrade gracefully: if OpenAI isn't configured, or fails mid-run, headlines still persist with story_id = NULL rather than being lost. That guarantee is worthless if the display layer then silently drops them or, worse, merges every ungrouped headline into one giant fake Story because they all share the same "key" (None). Both failure modes are real risks a naive groupby(story_id) would hit: 

def _group_into_stories(headlines: list[Headline]) -> list[dict]:
    groups: dict[object, list[Headline]] = {}
    for headline in headlines:
        key = headline.story_id if headline.story_id is not None else headline.id
        groups.setdefault(key, []).append(headline)
    ...

Falling back to the headline's own id when story_id is None gives every ungrouped headline its own unique group key — its own singleton Story — rather than colliding on the shared value None.

A real FK constraint, found only once the integration test needed it

Writing a test that seeds a headline with an arbitrary uuid4() as its story_id hit a real, previously-unexercised constraint: 

sqlalchemy.exc.IntegrityError: ForeignKeyViolationError: insert or update on table "headlines"
violates foreign key constraint "headlines_story_id_fkey"
DETAIL: Key (story_id)=(f701d546-...) is not present in table "stories".

headlines.story_id really does reference stories.id — no prior test had ever tried to fabricate a fake one. Fixed the same way production code always does it: create the real Story row first, then assign its actual id to the headline — not by loosening the test or the constraint.

Check your understanding

Q1. Why does this lesson replace the response shape outright instead of adding days alongside the existing today/recent fields, unlike every earlier lesson in this arc?

Reveal answer

Every earlier lesson's change was cheap to make additive (a nullable column, an unused table, one new field). Here, keeping both shapes alive would mean writing and testing two full reshaping paths for a frontend that's being rebuilt in the very next lesson anyway -- real extra cost for a transitional state nobody needs to see, on a personal project with no other users.

Q2. Why does _group_into_stories use the headline's own id as a fallback key instead of just grouping by story_id directly?

Reveal answer

Every headline with story_id=None would share the exact same key (None) under a plain groupby, silently merging every currently-ungrouped headline into one fake Story -- exactly the failure ADR 0012's graceful degradation exists to prevent. Falling back to each headline's own unique id keeps them as separate singleton Stories instead.

Q3. Why does build_daily_view bucket headlines into days before grouping them into Stories, rather than grouping into Stories first and deriving each Story's day from its primary?

Reveal answer

Both orders give the same answer today, since a Story's members always share one Eastern day by construction (ADR 0006's day-scoping). But bucketing by day first doesn't depend on that invariant holding -- it reflects each headline's own real day directly, rather than trusting that no Story could ever end up spanning two days.
