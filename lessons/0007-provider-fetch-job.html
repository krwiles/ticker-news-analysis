The provider-fetch job

ARQ's actual job-enqueue pattern, two real bugs a live check caught that reading the code never would have, and a caching design built to never write garbage in the first place.

The project's first real ARQ job

Every job so far has been cron_jobs — scheduled, nobody asks for it. This lesson adds functions: work triggered on demand, by something enqueueing it.

worker.py

async def fetch_headlines_job(ctx: dict, ticker: str) -> dict:
    return await fetch_and_persist_headlines(ticker)

class WorkerSettings:
    functions = [fetch_headlines_job]   # new
    cron_jobs = [cron(heartbeat, second=set(range(0, 60, 5)))]

fetch_headlines_job is a thin wrapper — the real logic (fetch_and_persist_headlines, in providers.py) takes no ARQ ctx at all. That's deliberate: a plain function is callable directly from a test (lesson 9) without spinning up a worker, and it's the same function a future scheduled watchlist feature will trigger via cron_jobs instead — one job, two different triggers, per ADR 0004.

Enqueueing and awaiting a result, for real, against the running stack:

job = await redis.enqueue_job('fetch_headlines_job', 'AMZN')
result = await job.result(timeout=90)
# {'status': 'success', 'providers': {'edgar': 'ok', 'finnhub': 'ok'}, 'headline_count': 249}

Caching a CIK without ever writing a garbage row

Fetching EDGAR filings needs a company's CIK, and SEC only offers that as one giant file covering every public company — expensive to re-fetch on every search. companies caches it. The interesting part is when a row gets written:

  1. SEC's mapping recognizes the ticker → row written immediately, cik and company_name both populated.
  2. SEC's mapping doesn't recognize it, but Finnhub still returns real headlines → row written now, with cik/company_name null — a real, permanent state, not a placeholder.
  3. Neither provider returns anything → no row, ever.

Verified live: searching a nonsense ticker (ZZZQX) created zero rows in either companies or headlines. No cleanup job needed for fake/typo'd tickers — the sequencing means nothing bad is ever written, rather than writing first and pruning later.

Two bugs a live check caught that reading the code wouldn't have

Both of these passed a code review in my own head. Neither survived contact with a real API response.

Bug 1 — no date filter on EDGAR filings. EDGAR's "recent filings" feed returns a company's most recent filings of any age — up to ~1000, spanning years. Filtering by form type alone isn't filtering by time. First real run against AAPL returned 159 filings going back to 2015, silently violating spec 0001's "past week" requirement. Fixed with the same kind of cutoff Finnhub's from/to params already handled — just missing on the EDGAR side.

Bug 2 — useless filing titles. The plan assumed primaryDocDescription would give a real description. Verified live, it just restates the form type: "10-Q: 10-Q", "8-K: 8-K". Fixed with an explicit lookup table ("8-K" → "Current Report (Material Event)") instead of trusting the field name's implication.

Confirmed fixed, against a real AMZN 8-K filed the day before this lesson was written:

title: "8-K: Current Report (Material Event)"
url:   https://www.sec.gov/Archives/edgar/data/1018724/000101872426000036/amzn-20260908.htm
published_at: 2026-09-09 20:28:21+00

Provider vs. Outlet, for real

Finnhub's own response has a source field — the actual original publisher ("Yahoo", "ChartMill") — separate from Finnhub itself, which is just the API being called. This is exactly the Provider/Outlet split from CONTEXT.md, confirmed against a real response rather than designed in the abstract: 

{"provider": "finnhub", "outlet": "Yahoo", "title": "Apple's Foldable Duo Represents ...",
 "summary": "Apple (AAPL) new foldable iPhone represents a \"notable form-..."}

Dependency injection, applied without a framework

Every fetch function takes its externals as parameters — client: httpx.AsyncClient, session_factory=async_session_factory — instead of importing them. No FastAPI, no Depends(), since this runs inside an ARQ job, not a request. Same principle, applied by hand: lesson 9's tests will pass in a mocked client and a test-database session factory, with zero changes to the functions themselves.

A judgment call worth naming, not hiding

Finnhub returns 403 Forbidden — not an empty list — for a ticker it doesn't recognize, with the message "You don't have access to this resource". That phrasing is genuinely ambiguous: it reads like a permissions problem, which it could also legitimately be (a revoked key, a plan restriction), not just "this ticker doesn't exist." Rather than guess, a 403 stays classified as a real "error" — the honest cost is a plain typo shows partial_failure instead of a cleaner "not found," but the alternative risks silently hiding a genuine access problem as if it were just an empty result.

Check your understanding

Q1. Why does fetch_and_persist_headlines take no ARQ ctx argument, even though it only ever runs as a job?

Reveal answer

So it's callable directly — from a test with no worker running (lesson 9), or later from a cron_jobs entry for the watchlist feature. worker.py's fetch_headlines_job is the only thing that knows ARQ exists at all.

Q2. A ticker is real and Finnhub has news for it, but SEC's mapping doesn't recognize it. What ends up in companies?

Reveal answer

A row with cik and company_name both null — written only because Finnhub returned real headlines that needed somewhere to point via the foreign key. That's a legitimate permanent state, not a bug to fix later.
