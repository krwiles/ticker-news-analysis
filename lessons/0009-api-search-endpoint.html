The /api/search endpoint

Two steps, not one — and the FastAPI-specific gotcha that broke every single request until it was found live.

Not one step — enqueue, then query

Easy to under-specify: lesson 7's job result is just a summary ({"status", "providers", "headline_count"}) — it never hands back the actual headlines, because it already persisted them. So this endpoint does two genuinely separate things in sequence:

  1. Enqueue and await the fetch job — makes sure Postgres has fresh data for this ticker.
  2. Query Postgres directly for that ticker's past week, split it, and shape the response.

A timeout in step 1 doesn't skip step 2 — the endpoint still returns whatever Postgres already has (from an earlier successful search, say), while honestly reporting complete_failure. Graceful degradation, not silence. Verified live by stopping the worker container entirely: 

status: complete_failure  providers: {}  today: 52  recent: 192

Real, existing data still came back — nothing was lost just because the fetch step failed.

FastAPI's Depends(), for real this time

Depends() has come up in conversation for a while; this is the first lesson that actually uses it. The ARQ Redis pool is created once, at app startup, the same lifetime reasoning as db.py's engine: 

@asynccontextmanager
async def api_lifespan(app: FastAPI):
    app.state.arq_redis = await create_pool(RedisSettings.from_dsn(settings.redis_url))
    yield
    await app.state.arq_redis.aclose()

async def get_arq_redis(request: Request) -> ArqRedis:
    return request.app.state.arq_redis

@router.get("/api/search")
async def search(ticker: str, arq_redis: ArqRedis = Depends(get_arq_redis), ...):

Only wired in for api mode — ui never enqueues a job, so it has no reason to hold a Redis pool open for its whole process lifetime.

A real bug, live, on the very first request. providers.py's functions take session_factory=async_session_factory as a plain default parameter — that's fine, because nothing inspects them. This endpoint copied that pattern and every request crashed: TypeError: cannot pickle 'module' object. The reason: a FastAPI path operation's parameters are actively introspected by the framework itself — to validate the request and build the OpenAPI docs. A raw async_sessionmaker object as a bare default isn't something FastAPI knows how to treat as request data, and it broke trying to deep-copy it. The fix is the same Depends() pattern as the Redis pool above — a tiny function returning the value, not the value itself as a default: 

def get_session_factory():
    return async_session_factory

async def search(..., session_factory = Depends(get_session_factory)):

The rule this leaves behind: plain-default dependency injection only works on functions nothing inspects. providers.py's functions qualify — they're just called directly. A FastAPI route never does — Depends() is mandatory there, not a style preference.

The Today/Recent split — same injection principle, applied on purpose this time

def split_today_recent(headlines: list[Headline], now: datetime) -> tuple[list[dict], list[dict]]:
    today_date = now.astimezone(EASTERN).date()
    ...

now is a parameter here too — not datetime.now() called inside the function. Same reasoning as client/session_factory in lesson 7: lesson 10's tests need to check the Eastern-midnight/DST boundary against a fixed fake time, not wait for real midnight to arrive.

A quieter bug: an empty error message

Verified during the worker-down test above: the log line for a failed job read {"error": "", ...} — blank. asyncio.TimeoutError() carries no message at all, so str(exc) is just an empty string. The fix records the exception's own type alongside its (possibly empty) message: f"{type(exc).__name__}: {exc}" — now a timeout is visibly a timeout in the logs, not just a blank field someone has to guess about later.

Check your understanding

Q1. Why does session_factory=async_session_factory work fine in providers.py but crash as a FastAPI route parameter?

Reveal answer

providers.py's functions are called directly — nothing inspects their signatures. FastAPI actively inspects every path-operation parameter to build request validation and OpenAPI docs; a non-JSON-friendly object as a bare default breaks that. Depends() tells FastAPI "don't treat this as request data."

Q2. The fetch job times out. Does /api/search return an empty response?

Reveal answer

No — it still runs step 2 (the Postgres query) regardless, and returns whatever's already there, with status: "complete_failure" reflecting the job problem honestly rather than hiding it.
