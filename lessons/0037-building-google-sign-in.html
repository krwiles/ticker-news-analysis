Building Google Sign-In

Spec 0006 and ADR 0016 already decided what to build and why. This lesson is the build itself — and two real gaps found only by checking the running container, not by trusting the design.

Lessons 35 and 36 covered the concepts this needed first — how one Redis serves both ARQ and sessions without colliding, and how OAuth/OIDC work in general. Spec 0006 (behavior) and ADR 0016 (Google Identity Services, `google-auth`, Redis-backed sessions, the cookie's exact attributes) were both already grilled and written down before any code existed. This lesson doesn't re-argue any of that — it's what actually happened turning those decisions into a working `POST /api/auth/google`, a `GET /api/auth/me`, a `POST /api/auth/logout`, and a button in the corner of every page.

The shape: one credential, three routes

The frontend never talks to Google's OAuth servers directly — Google's own GIS script does that. It renders a button; on success, it hands the frontend a signed ID token (a JWT, called a "credential" in GIS's own terminology) through a JS callback. No redirect, no authorization code. From there it's plain HTTP between this app's own frontend and backend: 

POST /api/auth/google  { "credential": "<GIS JWT>" }
  → verify it, upsert a User row, create a session, set an HttpOnly cookie

GET /api/auth/me
  → cookie in, {"user": ...} or {"user": null} out — never an error

POST /api/auth/logout
  → delete the Redis session key outright, clear the cookie

/api/auth/me exists at all because the cookie is HttpOnly by design (ADR 0016) — JavaScript can never read it, so the only way the frontend learns "am I signed in" is asking the backend, once, on every page load.

Sessions are just Redis calls — proven, not assumed

ADR 0016 noticed that ARQ's own ArqRedis class is a real subclass of redis.asyncio.Redis — meaning the pool search.py already opens for job enqueueing can also run plain GET/SET/EXPIRE/DELETE calls, no second connection pool needed. auth.py reuses search.py's existing get_arq_redis dependency directly: 

async def _create_session(redis: ArqRedis, sub: str) -> str:
    session_id = secrets.token_urlsafe(32)
    await redis.set(f"session:{session_id}", sub, ex=SESSION_TTL_SECONDS)
    return session_id

async def _resolve_session(redis: ArqRedis, session_id: str) -> str | None:
    sub = await redis.get(f"session:{session_id}")
    if sub is None:
        return None
    await redis.expire(f"session:{session_id}", SESSION_TTL_SECONDS)  # sliding window
    return sub.decode() if isinstance(sub, bytes) else sub

That the class hierarchy makes this possible is a fact about the library; that it actually behaves that way inside this app's own containers is a claim worth checking. So before writing any frontend code, a session key was set directly with redis-cli against the real running Redis, and /api/auth/me resolved a real user from it — then logout deleted it, confirmed by reading the key back and getting nothing. Same discipline as lesson 31's live curl checks: a class hierarchy is a reason to expect something works, not proof that it does.

An injectable verifier, so no test ever calls Google

search.py already has this pattern twice — get_arq_redis and get_session_factory are FastAPI dependencies real requests get one way, tests override with a fake. auth.py adds a third: 

def get_token_verifier():
    return _verify_google_credential   # real requests get this

# a test does:
app.dependency_overrides[get_token_verifier] = lambda: fake_verifier_returning({"sub": "...", ...})

Every backend test — new user created, existing user's name/picture refreshed without a second row, invalid credential rejected, all three signed-out shapes of /api/auth/me, logout actually deleting the Redis key — runs against a fake Redis and a fake verifier, never a real Google credential or a real network call.

Two real gaps, found by checking

1. The client ID never actually reached the container. docker-compose.yml's shared &app-env anchor forwards FINNHUB_API_KEY and OPENAI_API_KEY to every app container — but GOOGLE_CLIENT_ID was missing from that same list entirely. Nothing caught this at first: the "reject a malformed credential" test path fails the same way (a JWT parse error) whether or not settings.google_client_id is even set, so it looked done. It only surfaced by explicitly running settings.google_client_id inside the live container and seeing an empty string. Fixed by adding the line — but the real lesson is that a passing test for the failure path told nothing about whether the success path could ever work.

2. One except clause wasn't enough. google-auth's own docstring for verify_oauth2_token says: 

Raises:
    exceptions.GoogleAuthError: If the issuer is invalid.
    ValueError: If token verification fails

The first draft only caught ValueError — the more common case (bad signature, expired token), and the one every quick example online shows. A wrong-issuer token would have raised GoogleAuthError straight through as an unhandled 500 instead of a clean 401. Reading the library's own docstring, not a tutorial's simplified try/except, is what caught it — the fix catches both, and a dedicated test patches id_token.verify_oauth2_token to raise each one in turn and confirms both collapse to the same TokenVerificationError.

The frontend: one dependency, one component

index.html gets a single <script> tag pointing at Google's own GIS script — no npm package, matching how this project already avoids frontend build-time env injection (config.ts's API_BASE_URL is hardcoded the same way, and now GOOGLE_CLIENT_ID joins it — not a secret, safe to ship, ADR 0016). GIS has no official TypeScript types, so AuthControls.tsx declares just the two methods it actually calls on window.google.accounts.id, not a full type package for two methods.

AuthControls itself is a small state machine: fetch /api/auth/me once on mount to learn the truth (nothing renders until that resolves, avoiding a signed-out flash for someone actually signed in); render GIS's button if signed out; render name, picture, and a sign-out button if signed in. It's mounted once, in Layout, so it's the same control in the same place on every route — literally spec 0006's own wording.

Check your understanding

Q1. Why does this app need a GET /api/auth/me endpoint at all, instead of just reading the session cookie's value in JavaScript on page load?

Reveal answer

The cookie is set HttpOnly (ADR 0016) specifically so JavaScript can never read or tamper with it — it only ever travels automatically with a request. Since the frontend has no way to inspect the cookie's contents itself, the only way to learn "who is this session, if anyone" is to ask the backend, which can actually read it and look the session up in Redis.

Q2. Why didn't the missing GOOGLE_CLIENT_ID in docker-compose.yml get caught by testing the rejected-credential path?

Reveal answer

A malformed JWT fails to even parse as a token, which happens before the audience (client ID) is ever checked against anything — so that test passes identically whether the real client ID is configured or not. Only a real, well-formed credential's audience check would have exposed the gap, and nothing in the test suite exercises that (tests use an injected fake verifier by design). Catching it required explicitly checking the setting's actual value inside the running container.

Q3. Why does auth.py import get_arq_redis and get_session_factory from search.py rather than defining its own copies?

Reveal answer

FastAPI's dependency_overrides work by the exact function object being overridden. Two separate functions that each return the same pool would need two separate overrides kept in sync in every test, and in production they'd still just be two names for the same one real pool — sharing the one dependency is simpler and makes both routers overridable from a single point.
