OAuth at a high level: how "Sign in with Google" actually works

Not Google-specific mechanics — the same shape every "Sign in with X" button uses, so it transfers directly to GitHub, Microsoft, or whatever spec 0006's "door open for more providers later" eventually points at.

One thing to unlearn first: OAuth's job is authorization — "can this app do something on my behalf" — not identity. "Sign in with Google" layers identity on top of that (more on this below), but the underlying dance is the same either way.

The four actors

Every OAuth flow, for any provider, involves the same four roles:

  • Resource Owner — the real person, sitting at their browser.
  • Client — this app, wanting to know who that person is.
  • Authorization Server — Google's own login/consent system (or GitHub's, or Microsoft's).
  • Resource Server — the API that actually holds the data the Client wants (here, just "who is this person").

For a plain sign-in, the Authorization Server and Resource Server are effectively the same place (Google), but the roles are still worth naming separately — a different OAuth use case (say, an app that reads your Google Calendar) makes the Resource Server a genuinely distinct API the Authorization Server merely grants access to.

The actual dance, step by step

  1. The app redirects the browser to the provider's own authorization endpoint, with its client ID, the permissions it's asking for (scopes), and a random anti-forgery value (state).
  2. The provider handles login and shows the consent screen entirely on its own — the app never sees the person's password, ever.
  3. On approval, the provider redirects the browser back to the app with a one-time-use authorization code, plus the same state value echoed back.
  4. The app's server — not the browser — sends that code, along with its client secret, directly to the provider's token endpoint.
  5. The provider replies with tokens: an ID token (a signed statement of who the person is) and often an access token (permission to call the Resource Server's API).
  6. The app verifies the ID token — its signature against the provider's published public keys, plus the issuer, audience, and expiry — before trusting anything it says.

Why the client secret never touches the browser

Step 4 happens server-to-server specifically because a secret embedded anywhere in browser-delivered code (JavaScript, a mobile app binary) isn't actually secret — anyone can extract it. The one-time authorization code from step 3 is safe to pass through the browser precisely because it's useless without the client secret to redeem it, and that secret only ever exists on the app's own server.

OAuth vs. OpenID Connect — the actual distinction

OAuth 2.0 itself has no formal concept of "identity" — it's purely about authorization tokens for accessing an API. OpenID Connect (OIDC) is a thin identity layer built on top of OAuth 2.0 that adds exactly one new thing: the ID token, a signed JWT that says "this is who signed in." Every "Sign in with Google/GitHub/Microsoft" button in the wild is technically OIDC, not bare OAuth — the term "OAuth login" is common shorthand, but the identity part specifically comes from OIDC riding on top.

What state and nonce actually prevent

state (step 1/3) stops a specific attack: a malicious site tricking a signed-in user's browser into completing a login flow the user never actually started, by replaying a stolen authorization code. The app checks that the state it gets back matches the one it sent — a mismatch means the flow didn't originate from this app's own request. nonce is the OIDC-specific cousin: a value embedded inside the ID token itself, checked to make sure a captured token can't be replayed later as if it were fresh.

Why this generalizes cleanly to "more providers later"

Every real provider — Google, GitHub, Microsoft, anyone implementing OAuth2/OIDC — exposes the identical shape: an authorization endpoint, a token endpoint, scopes, redirect URIs. What differs is just the specific URLs, the exact scope names, and the shape of the claims inside the ID token. That's precisely why spec 0006's "door open for more providers later, no account-linking decided yet" is realistic rather than wishful: adding a second provider later means pointing the same client library at a different provider's configuration, not re-deriving this whole flow from scratch.

Check your understanding

Q1. Is "Sign in with Google" OAuth or OpenID Connect?

Reveal answer

Technically OpenID Connect — OAuth 2.0 itself carries no identity concept, only authorization tokens. OIDC is the identity layer on top that adds the ID token, which is what actually says who signed in. "OAuth login" is the common colloquial name, but the identity part specifically comes from OIDC.

Q2. Why does the authorization-code-for-token exchange have to happen from the app's server, never from JavaScript running in the browser?

Reveal answer

That exchange requires the client secret, and any secret shipped to the browser (in JS, in a mobile app binary) can be extracted by anyone — it isn't actually secret once it's client-side. The one-time authorization code is safe to pass through the browser precisely because it's useless without the secret, which only ever lives on the server.

Q3. What specific attack does the state parameter prevent?

Reveal answer

A malicious site tricking a user's browser into completing a login flow the user never initiated (a cross-site request forgery on the login flow itself), often by replaying a stolen authorization code. The app generates a random state value before redirecting and rejects the callback if the state that comes back doesn't match, proving the flow really originated from this app's own request.

Q4. Why is adding a second sign-in provider later expected to be straightforward, not a redesign?

Reveal answer

Every real OAuth2/OIDC provider implements the identical shape — an authorization endpoint, a token endpoint, scopes, redirect URIs. Only the specific URLs, scope names, and claim formats differ between providers. A client library configured for one provider is reconfigured for another, not rebuilt.
